Networking Foundations Primer

Universal dependency chain: learn/originate → policy → advertisement/import → RIB selection → recursive resolution → FIB/adjacency/tunnel/label programming → packet forwarding → remote delivery → return path.

Control plane vs data plane

The control plane learns topology, routes, labels, memberships and policy. The data plane is the FIB, adjacency, tunnel, label stack, ECMP group or ASIC/kernel state that moves packets.

Route, prefix, next hop

A prefix describes destinations, a route is one candidate path, and a next hop is the immediate or recursively resolved forwarding target.

RIB, FIB, adjacency

The RIB selects reachability. The FIB is forwarding-ready state. An adjacency is the final neighbor/tunnel/label relationship needed to transmit.

Recursive next-hop resolution

A BGP/overlay next hop can resolve through another route repeatedly until the chain reaches a connected adjacency, tunnel or failure.

Administrative distance / route preference

When protocols offer the same prefix, platforms use a cross-protocol preference before programming forwarding.

Underlay / overlay

The underlay reaches infrastructure endpoints. VXLAN, EVPN, MPLS and other overlays depend on it while maintaining separate service state.

VXLAN / VTEP / VNI

VXLAN encapsulates traffic in UDP/IP. VTEPs add/remove encapsulation. A VNI identifies a logical L2 or L3 service.

EVPN / RD / RT

EVPN uses BGP for endpoint/service reachability. RD makes VPN routes unique; RT determines import/export membership.

IRB / anycast gateway

IRB connects bridging and routing. Anycast gateway presents the same first-hop identity on multiple fabric nodes.

BUM

Broadcast, unknown-unicast and multicast need replication or multicast handling because a single known remote unicast destination is absent.

Redistribution / filtering / tagging

Redistribution re-originates routes between protocols. Tags, communities, prefix lists and route maps preserve intent and prevent feedback.

LACP / ESI / DF

LACP negotiates bundles. EVPN ESI identifies a multihomed segment and DF election coordinates selected BUM forwarding.

VRF / VLAN / trunk

A VRF is an isolated Layer-3 table, a VLAN is an L2 broadcast domain, and a trunk carries multiple VLANs.

1. Cisco Systems — OSPFv3 Prefix Suppression

Exact source: https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-routing/b-ip-routing/m_iro-pref-supp-v3.html

Beginner foundation — terms you need before this lesson

OSPFv3 separates topology from addressing more cleanly than OSPFv2. Router- and Network-LSAs describe links; Intra-Area-Prefix and Link LSAs carry prefixes. Prefix suppression removes transit-interface prefixes from those prefix-carrying LSAs while preserving the topology needed for SPF.

Problem / why the feature exists

Large routed fabrics often do not need every point-to-point transit prefix reachable from everywhere. Suppressing those addresses reduces LSA storage, flooding work and the attack surface while keeping loopbacks, secondary addresses and passive-interface prefixes reachable.

Architecture, protocol mechanics and state sequence

The OSPFv3 process builds topology LSAs → prefix suppression removes eligible local transit prefixes from prefix-carrying LSAs → neighbors still run SPF over the same links → next-hop calculations use link-local adjacency information → only intentionally retained prefixes remain globally routable.

Source-supported configuration / verification

Cisco documents `prefix-suppression` under the OSPFv3 IPv6 unicast address family and per-interface controls. `show ospfv3` confirms process behavior. A healthy adjacency does not prove a transit prefix is being advertised; inspect the OSPFv3 database and route table.

Failure mode, design consequence and reproducible lab

A management tool that tries to reach a suppressed transit address can fail while traffic through the link works perfectly. Do not misdiagnose that as an adjacency failure. In a lab, compare the database before/after suppression and verify loopbacks remain reachable.

2. Cisco Systems — IS-IS IPv6 Multitopology Transition Mode

Exact source: https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-routing/b-ip-routing/m_ip6-route-mult-isis-xe.html

Beginner foundation — terms you need before this lesson

Single-topology IS-IS requires IPv4 and IPv6 to share one topology. Multitopology IS-IS runs separate SPF views per address family, allowing a link to carry one family but not the other. Transition mode advertises both styles while a domain is being upgraded.

Problem / why the feature exists

A direct jump from single-topology to multitopology can create IPv6 holes because routers in the two modes interpret capability/topology information differently. Transition mode provides a controlled migration stage.

Architecture, protocol mechanics and state sequence

Existing routers run single-topology → upgraded routers enable `multi-topology transition` and advertise both compatible TLV forms → every router is moved to transition → after the entire area/domain supports MT, transition is removed → IPv4 and IPv6 can then use independent metrics/topologies.

Source-supported configuration / verification

Cisco requires wide metrics for IPv6 MT because the relevant TLVs use extended metrics. The address family uses `multi-topology [transition]`; interfaces can use `isis ipv6 metric` to diverge IPv6 cost from IPv4.

Failure mode, design consequence and reproducible lab

Removing transition too early can isolate IPv6 while IPv4 remains healthy. Validate LSP capability/TLVs and per-family routes on every node before the final step.

3. Cisco Systems — BGP Route Flap Dampening

Exact source: https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-routing/b-ip-routing/m_irg-int-features-0.html

Beginner foundation — terms you need before this lesson

Route flap dampening assigns a penalty to unstable BGP routes. Penalty decays with a half-life. Above the suppress threshold the route is hidden; below the reuse threshold it becomes usable again.

Problem / why the feature exists

An unstable external prefix can consume CPU and propagate repeated UPDATE/WITHDRAW churn. Dampening trades some reconvergence speed for stability.

Architecture, protocol mechanics and state sequence

External path flaps → penalty accumulates → when suppress threshold is crossed the path enters damped state and is not advertised/selected → penalty decays → below reuse threshold the path is restored → history eventually ages out.

Source-supported configuration / verification

Cisco documents `bgp dampening` and `show ip bgp dampening flap-statistics` / `dampened-paths`. Default examples include a 15-minute half-life, suppress threshold 2000 and reuse threshold 750. Cisco notes external routes learned through iBGP are not dampened in the same way.

Failure mode, design consequence and reproducible lab

Clearing dampening makes a prefix immediately usable but does not repair the flapping circuit. First prove whether the route is absent because of current reachability or historical penalty.

4. Palo Alto Networks — ECMP Multiple-AS Support for BGP

Exact source: https://docs.paloaltonetworks.com/ngfw/networking/ecmp/enable-ecmp-for-multiple-bgp-autonomous-systems

Beginner foundation — terms you need before this lesson

Normal BGP ECMP often expects candidate paths to have compatible neighboring-AS properties. PAN-OS exposes an explicit ECMP Multiple AS Support option when equal-cost exits are learned through different upstream ASes.

Problem / why the feature exists

A firewall multihomed to two ISPs may have two otherwise-equal BGP paths but use only one unless cross-AS ECMP behavior is enabled.

Architecture, protocol mechanics and state sequence

BGP receives equal candidates from different upstream ASes → BGP best-path and ECMP eligibility are evaluated → ECMP Multiple AS Support permits both to enter the forwarding ECMP set → the session hash chooses a member for each flow.

Source-supported configuration / verification

PAN-OS documents Network > Virtual Routers > BGP > Advanced > ECMP Multiple AS Support, after ECMP itself is enabled. Verify both BGP candidate routes and the forwarding table; enabling the checkbox alone does not manufacture equal paths.

Failure mode, design consequence and reproducible lab

Different LOCAL_PREF, AS-path length, MED policy, recursive cost or unresolved next hop can still prevent ECMP. First determine which best-path attribute disqualifies the second path.

5. Palo Alto Networks — RIPv2 Default Advertisement Independent of RIB Default

Exact source: https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing/configure-ripv2-on-an-advanced-routing-engine

Beginner foundation — terms you need before this lesson

A routing protocol can originate a default route as policy even when the local RIB does not contain 0.0.0.0/0. PAN-OS ARE explicitly supports advertising a default in RIP without requiring an installed default.

Problem / why the feature exists

Small branch designs sometimes need the firewall to tell downstream RIP routers 'send unknown traffic here' even when the firewall itself reaches destinations through more-specific dynamic routes.

Architecture, protocol mechanics and state sequence

RIP process has default-advertisement enabled → it originates 0.0.0.0/0 into RIP updates → downstream router installs the default according to RIP preference/metric → traffic arrives at the firewall → the firewall then performs its own independent RIB lookup.

Source-supported configuration / verification

PAN-OS ARE documents the `advertise default route in RIP` option. Verify the downstream route table and the firewall's own ability to forward destinations; the advertisement can exist even if the local RIB lacks a default.

Failure mode, design consequence and reproducible lab

This can create a black hole if the firewall cannot actually reach arbitrary destinations. Validate data-plane reachability before treating successful RIP default advertisement as service readiness.

6. Palo Alto Networks — OSPF SPF Calculation Delay and LSA Interval Tuning

Exact source: https://docs.paloaltonetworks.com/ngfw/help/11-1/network/network-virtual-routers/ospf/ospf-advanced-tab

Beginner foundation — terms you need before this lesson

SPF Calculation Delay controls how soon a router recomputes shortest paths after topology information changes. LSA Interval controls the minimum time between two instances of the same LSA, corresponding to OSPF MinLSInterval behavior.

Problem / why the feature exists

Aggressive convergence settings reduce outage time but can amplify CPU load during instability. Conservative settings reduce churn but delay recovery.

Architecture, protocol mechanics and state sequence

Topology change occurs → LSA origination is gated by the LSA interval → neighbors receive/flood the update → SPF calculation waits according to the configured delay → new routes are selected and programmed.

Source-supported configuration / verification

PAN-OS exposes both timers in OSPF Advanced settings. Peer devices should be tuned coherently. Inspect OSPF event timing, LSDB update times and route installation rather than assuming a low Hello timer alone controls convergence.

Failure mode, design consequence and reproducible lab

If LSAs arrive quickly but route changes occur late, SPF delay is the likely boundary. If the local router cannot originate repeated LSAs quickly, the LSA interval is the boundary.

7. Fortinet — BGP Maximum-Prefix Threshold and Warning-Only Behavior

Exact source: https://docs.fortinet.com/document/fortigate/7.6.6/cli-reference/225427711/config-router-bgp

Beginner foundation — terms you need before this lesson

Maximum-prefix protects a BGP neighbor from sending an unexpectedly large table. Threshold is a percentage warning point; warning-only changes the over-limit action from session-disruptive protection to notification.

Problem / why the feature exists

Route leaks can consume memory/CPU or overwrite intended policy. A prefix ceiling provides a last-resort guardrail.

Architecture, protocol mechanics and state sequence

Neighbor advertises routes → accepted-prefix counter rises → percentage threshold generates early warning → absolute maximum is crossed → default enforcement or warning-only behavior applies depending on configuration.

Source-supported configuration / verification

FortiOS exposes `maximum-prefix`, AF-specific variants, `maximum-prefix-threshold`, and `maximum-prefix-warning-only`. Verify per-neighbor received/accepted counts and the configured AF; an IPv4 limit does not protect EVPN/VPNv4/IPv6 unless their own controls exist.

Failure mode, design consequence and reproducible lab

Raising the limit after a leak can merely postpone failure. Identify which policy or peer caused the unexpected growth before restoring unrestricted exchange.

8. Fortinet — BGP Next-Hop Tag-Match Resolution

Exact source: https://docs.fortinet.com/document/fortigate/7.6.3/administration-guide/245878/bgp-next-hop-tag-match-mode

Beginner foundation — terms you need before this lesson

Recursive BGP next-hop resolution normally uses longest/best matching routes. FortiOS tag-resolve-mode can instead prefer resolution through routes carrying the same tag or merge tag-match and best-match results.

Problem / why the feature exists

Dual-hub SD-WAN/ADVPN designs can resolve a reflected BGP route through the wrong hub even though IP longest-match is valid. Tags preserve path affinity across recursion.

Architecture, protocol mechanics and state sequence

BGP route carries/associates a tag → recursive resolver searches candidate next-hop routes → `preferred` uses same-tag resolution when available → `merge` can combine tagged and ordinary matches while excluding duplicate-interface outcomes → selected recursive next hops feed forwarding.

Source-supported configuration / verification

FortiOS documents `set tag-resolve-mode {disable|preferred|merge}`. Inspect the route table's recursive next hops and route tags; do not infer path affinity from the BGP best path alone.

Failure mode, design consequence and reproducible lab

A route can be BGP-best yet resolve through a hub that cannot forward it. The failure boundary is recursion policy, not path selection.

Exact source: https://docs.fortinet.com/document/fortigate/7.6.3/cli-reference/183110249/config-router-multicast

Beginner foundation — terms you need before this lesson

PIM neighbors discover each other with Hello messages. On multiaccess networks, DR priority influences Designated Router election. Hello interval controls transmission frequency; holdtime controls neighbor expiry.

Problem / why the feature exists

Multicast first-hop/last-hop behavior can become unstable when DR election or neighbor liveness timers are inconsistent across a LAN.

Architecture, protocol mechanics and state sequence

Source-supported configuration / verification

Failure mode, design consequence and reproducible lab

A physical interface can remain Up while PIM neighbor state expires. A DR change can alter who sends Registers/joins without changing unicast routing.

10. Arista Networks — Static Definition of BGP Flowspec Rules

Exact source: https://www.arista.com/en/support/toi/eos-4-33-0f

Beginner foundation — terms you need before this lesson

BGP Flowspec advertises traffic-match rules rather than ordinary destination prefixes. Match components can describe source/destination, ports, protocol, flags and other packet fields; actions can discard, rate-limit or redirect.

Problem / why the feature exists

Earlier EOS deployments often relied on an external controller to inject Flowspec. Static definition lets an operator create a rule locally, redistribute it into BGP and optionally install enforcement locally.

Architecture, protocol mechanics and state sequence

Source-supported configuration / verification

Failure mode, design consequence and reproducible lab

A rule can be present in BGP but not enforced if installation/policy is disabled. Conversely, local enforcement does not prove the rule was exported to peers.

12. Arista Networks — BGP AS-Path Multipath Relax

Exact source: https://www.arista.com/en/um-eos/eos-border-gateway-protocol-bgp

Beginner foundation — terms you need before this lesson

BGP ECMP normally imposes equivalence checks beyond simple metric equality. `bgp bestpath as-path multipath-relax` permits eBGP paths with equal AS-path length but different AS contents to participate in ECMP.

Problem / why the feature exists

A leaf or edge router may have equally good paths through different upstream AS sequences and want to use them concurrently.

Architecture, protocol mechanics and state sequence

Source-supported configuration / verification

Failure mode, design consequence and reproducible lab

Equal AS-path length alone is insufficient if LOCAL_PREF, origin, MED rules, IGP recursion or other earlier best-path criteria differ.

13. FRRouting — RFC 8212 eBGP Requires Policy

Exact source: https://docs.frrouting.org/en/latest/bgp.html#require-policy-on-ebgp

Beginner foundation — terms you need before this lesson

RFC 8212 changes safe eBGP behavior: routes should not be imported or exported unless explicit policy is attached. FRR's traditional profile enables this safety default.

Problem / why the feature exists

A newly established eBGP session should not accidentally exchange a full table simply because the operator forgot filters.

Architecture, protocol mechanics and state sequence

Source-supported configuration / verification

Failure mode, design consequence and reproducible lab

An Established session with zero accepted prefixes is not necessarily a transport problem. Missing policy can be the intentional reason.

14. FRRouting — PIM ECMP Rebalance

Exact source: https://docs.frrouting.org/en/latest/pim.html#ecmp

Beginner foundation — terms you need before this lesson

PIM RPF resolution can return several equal-cost upstream next hops. `ecmp` spreads (S,G) state across them; `ecmp rebalance` changes how existing flows are redistributed after a member fails.

Problem / why the feature exists

Without rebalance, only multicast flows that used the failed interface move, so surviving links can remain unevenly loaded.

Architecture, protocol mechanics and state sequence

Unicast RPF lookup returns ECMP set → PIM hashes (S,G) entries across members → one interface fails → basic ECMP moves affected flows only; rebalance recomputes distribution for all (S,G) states across the remaining set.

Source-supported configuration / verification

FRR documents `ecmp` and `ecmp rebalance` in PIM and notes they are VRF-aware. Verify RPF next-hop set and per-(S,G) outgoing/upstream choice before and after failure.

Failure mode, design consequence and reproducible lab

A multicast imbalance after a failure can be expected behavior if rebalance is disabled, not evidence of broken unicast ECMP.

15. FRRouting — RIP Offset Lists for Directional Metric Manipulation

Exact source: https://docs.frrouting.org/en/latest/ripd.html

Beginner foundation — terms you need before this lesson

RIP uses hop count. An offset list adds metric to selected routes in a specific inbound or outbound direction, optionally on a particular interface.

Problem / why the feature exists

Simple RIP domains sometimes need to make one path less attractive without rewriting every prefix or changing physical topology.

Architecture, protocol mechanics and state sequence

RIP update arrives or is prepared for send → access list/prefix match determines whether offset applies → configured metric is added → resulting hop count participates in RIP best-path selection; metric 16 remains unreachable.

Source-supported configuration / verification

Failure mode, design consequence and reproducible lab

Applying an offset in the wrong direction can change the neighbor's choice instead of the local router's choice. Excessive offset can poison a route by reaching 16.

16. Juniper Networks — BGP Out-Delay Per-Prefix Advertisement Pacing

Exact source: https://www.juniper.net/documentation/us/en/software/junos/cli-reference/topics/ref/statement/out-delay-edit-protocols-bgp.html

Beginner foundation — terms you need before this lesson

`out-delay` is not a session MRAI. It delays export of each prefix from the routing table into BGP until that route has remained present for the configured interval.

Problem / why the feature exists

Rapid best-path oscillation can create bursts of BGP updates. Per-prefix delay can smooth that churn at the cost of slower convergence.

Architecture, protocol mechanics and state sequence

RIB selects a new active route → out-delay timer starts for that prefix → if the route persists through the timer it is exported into BGP → BGP advertises it to peers. Initial exchange after session establishment is not delayed the same way.

Source-supported configuration / verification

Junos documents `out-delay` from 0 to 65535 seconds and displays the value as Outbound Timer in `show bgp group` output.

Failure mode, design consequence and reproducible lab

If a route is active locally but absent from outbound BGP for exactly the configured delay, that can be intended pacing rather than export-policy failure.

17. Juniper Networks — Deferred Initial BGP Multipath Build

Exact source: https://www.juniper.net/documentation/us/en/software/junos/cli-reference/topics/ref/statement/defer-initial-multipath-build-edit-protocols-bgp-family-inet-unicast.html

Beginner foundation — terms you need before this lesson

With multipath and Add-Path, BGP can repeatedly rebuild a multipath object as paths stream in. `defer-initial-multipath-build` waits for End-of-RIB or a maximum delay before doing the expensive initial calculation.

Problem / why the feature exists

Large route-reflector or edge tables can spend CPU rebuilding the same ECMP object many times during initial convergence.

Architecture, protocol mechanics and state sequence

Peer comes Up → routes stream in → normal behavior queues repeated multipath calculations → with defer enabled calculations wait → End-of-RIB or maximum-delay releases the build → final multipath object is resolved once the initial set is substantially complete.

Source-supported configuration / verification

Junos documents `defer-initial-multipath-build` and a `maximum-delay` option. A related `multipath-build-priority` can lower job priority instead of fully deferring the initial calculation.

Failure mode, design consequence and reproducible lab

During the defer window, lack of final ECMP width is not necessarily a missing path. Distinguish received BGP paths from completed multipath resolution.

18. Juniper Networks — Add-Path Path-Selection Mode: All Paths vs Equal-Cost Paths

Exact source: https://www.juniper.net/documentation/us/en/software/junos/cli-reference/topics/ref/statement/send-edit-protocols-bgp.html

Beginner foundation — terms you need before this lesson

Add-Path can advertise more than one path for a prefix. Junos `path-selection-mode` decides whether the send set is all eligible paths or only equal-cost paths.

Problem / why the feature exists

A route reflector may need broad path diversity for downstream policy, or only ECMP contributors for forwarding diversity. Those are different information goals.

Architecture, protocol mechanics and state sequence

BGP receives several paths → add-path send policy selects the prefix → path-selection-mode builds either all-path or equal-cost candidate set → path-count caps advertisements → path identifiers distinguish the multiple NLRIs.

Source-supported configuration / verification

Junos documents `all-paths` and `equal-cost-paths`, up to 64 Add-Path routes subject to limits, and notes that `path-selection-mode` and `multipath` cannot both be enabled in the same way.

Failure mode, design consequence and reproducible lab

A receiver seeing fewer paths than expected may be constrained by prefix policy, path-count, selection mode or capability negotiation; inspect each boundary separately.

19. Aruba/HPE — MPLS LDP Graceful-Restart Timer Ordering

Exact source: https://www.arubanetworks.com/techdocs/AOS-CX/10.13/PDF/mpls_6400-8360.pdf

Beginner foundation — terms you need before this lesson

LDP graceful restart preserves label forwarding while the LDP control session restarts. AOS-CX exposes forwarding-holding, max-recovery and neighbor-liveness timers and documents interaction with IGP/BGP graceful-restart timing.

Problem / why the feature exists

If LDP control state restarts but forwarding labels are deleted too soon, an otherwise recoverable control-plane restart becomes traffic loss.

Architecture, protocol mechanics and state sequence

Control plane restarts → forwarding-holding preserves MPLS entries → neighbor-liveness bounds how long the device waits for LDP session return → after reestablishment stale bindings may remain through max-recovery → fresh labels replace stale state.

Source-supported configuration / verification

AOS-CX documents `graceful-restart-timers` and recommends OSPF GR timer < LDP forwarding-holding < BGP GR timer. Changing LDP GR timer values can restart LDP sessions.

Failure mode, design consequence and reproducible lab

A timer change itself may disrupt the session. Validate timer hierarchy before changing production values and prove LFIB retention during a controlled restart.

20. Aruba/HPE — BGP Aggregate Split-Horizon Control

Exact source: https://developer.arubanetworks.com/aoscx/v10.13/reference/post_system-vrfs-vrf-name-bgp-routers

Beginner foundation — terms you need before this lesson

Aggregate split horizon controls whether a BGP aggregate is advertised back toward a peer that contributed the same network. It is separate from ordinary route reflection or IGP split horizon.

Problem / why the feature exists

An aggregate generated from learned components can be fed back toward the contributor, creating confusing reachability or policy behavior.

Architecture, protocol mechanics and state sequence

More-specific route is learned → BGP aggregate is synthesized → export processing checks aggregate split-horizon setting → when enabled the aggregate is withheld from the peer that advertised the contributing network.

Source-supported configuration / verification

AOS-CX REST BGP router schema exposes `agg_split_horizon` and describes the behavior. Verify the contributor relationship and advertised-routes view; an aggregate existing locally does not prove it should be sent back.

Failure mode, design consequence and reproducible lab

Disabling split horizon may be intentional in a special design, but it changes what the contributing peer sees. Test loop prevention and next-hop behavior before doing so.

21. Aruba/HPE — OSPFv3 Per-Interface BFD Override

Exact source: https://developer.arubanetworks.com/aoscx/v10.13/reference/post_system-interfaces

Beginner foundation — terms you need before this lesson

OSPFv3 can have a router-wide BFD policy, but AOS-CX permits an interface to override that global state with enable, disable or default behavior.

Problem / why the feature exists

A network may need BFD on high-value point-to-point links while leaving it disabled on slower or incompatible interfaces without creating separate OSPF processes.

Architecture, protocol mechanics and state sequence

OSPFv3 interface inherits router BFD default → interface override is evaluated → when enabled, BFD session liveness drives fast OSPFv3 neighbor failure → when disabled, OSPFv3 falls back to its normal Hello/Dead detection.

Source-supported configuration / verification

AOS-CX v10.13 REST interface schema exposes the OSPFv3 BFD override plus BFD minimum receive interval. Verify both the interface override and actual BFD session state.

Failure mode, design consequence and reproducible lab

Setting the override to enable does not prove a BFD peer formed. If the remote side is not configured, OSPFv3 may still rely on ordinary timers depending on platform behavior/configuration.
