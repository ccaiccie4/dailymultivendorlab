Networking Foundations Primer

Control plane vs data plane. The control plane learns and chooses reachability. The data plane actually forwards packets. A routing protocol can look healthy while forwarding is broken if the chosen route never becomes usable forwarding state.

Route, prefix and next hop. A prefix identifies a destination range such as 10.10.0.0/16. A route is a candidate path to that prefix. The next hop is the immediate or recursively resolved forwarding target.

RIB and FIB. The Routing Information Base stores route candidates and the selected route. The Forwarding Information Base is the forwarding-ready result programmed into hardware or the operating-system kernel.

Recursive next-hop resolution. A BGP or policy route may point to an address that is not directly connected. The router must find another route that reaches that next hop before the original route can forward.

Administrative distance / route preference. When several protocols offer the same prefix, the router uses a local trust/preference value to choose among protocols. Cisco commonly calls this administrative distance; Junos calls it route preference. Lower is generally preferred.

Underlay vs overlay. The underlay is the IP transport that makes infrastructure addresses reachable. An overlay builds logical services on top. VXLAN is an overlay encapsulation. A VTEP adds/removes VXLAN. A VNI separates logical segments. An L2VNI represents a Layer-2 segment; an L3VNI represents a tenant routing context in symmetric IRB.

EVPN, RD and RT. EVPN is a BGP address family used to advertise MAC, IP and prefix reachability. A Route Distinguisher makes otherwise identical VPN routes unique; Route Targets control import/export policy between VPN routing contexts.

IRB and anycast gateway. Integrated Routing and Bridging lets a fabric bridge within subnets and route between them. Anycast gateway means multiple fabric nodes present the same first-hop gateway identity so a host can use a local gateway after movement.

BUM. Broadcast, unknown-unicast and multicast traffic cannot always use a single known destination entry, so an overlay needs replication or multicast handling.

Redistribution. Redistribution copies selected routes from one routing source into another. It is useful at protocol boundaries but can create feedback loops and metric distortion. Tags, prefix policy and clear route ownership are the main safeguards.

LACP, MLAG/vPC/VSX and EVPN multihoming. LACP bundles physical links. Multichassis technologies let links terminate on two physical switches while appearing as one logical partner. EVPN multihoming uses an Ethernet Segment Identifier and Designated Forwarder election to coordinate multihomed segments across an EVPN control plane.

Mental model used throughout this workbook: learn/originate → apply policy → advertise/import → select in RIB → recursively resolve next hop → program FIB/adjacency → encapsulate if needed → forward → verify remote delivery and return path.

1. Cisco — BFD-EIGRP Support on IOS XE 26.x

Official • Catalyst 9200 / IOS XE 26.x • updated March 31, 2026
Source: https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9200/software/release/26-x/configuration_guide/rtng/b_26x_rtng_9200_cg/configuring_bfd_eigrp_support.html

Beginner foundation — terms you need before this lesson. EIGRP is Cisco’s advanced distance-vector IGP. BFD is a lightweight liveliness protocol that detects forwarding-path failure faster and more consistently than waiting for a routing protocol’s own hello timer. EIGRP becomes a BFD client: BFD watches the path, EIGRP reacts.

Why the feature exists

EIGRP already knows how to detect neighbor loss, but normal hello/hold timers may not meet sub-second convergence goals. BFD separates detection from route computation. That lets several protocols use one fast detector rather than independently tuning aggressive hello timers.

Control-plane sequence

EIGRP first forms its normal adjacency. Interface BFD timing is configured, then EIGRP registers neighbors with BFD. BFD exchanges control packets at negotiated rates. Missed packets beyond the detection multiplier move the session Down. EIGRP receives the failure notification, removes the neighbor, withdraws affected reachability and runs DUAL to find a feasible alternate.

Commands as questions

bfd interval <ms> min_rx <ms> multiplier <n>
router eigrp <asn>
 bfd all-interfaces
show bfd neighbors details

The first asks, “What detection timing should this interface attempt?” The second asks EIGRP to register with BFD. The show command asks whether the BFD session is actually Up and what timers/discriminators were negotiated. An Up BFD session proves liveliness between peers, not the health of every application path through the routers.

Failure evidence and troubleshooting

If EIGRP repeatedly resets while the interface remains up, inspect physical counters, BFD state/timers, CoPP/ACL treatment, and then EIGRP topology. Do not immediately increase EIGRP timers; that changes the consumer, not the failed detector. One-way forwarding failure is a classic case where carrier stays up but BFD detects trouble.

Lab: compare convergence with native EIGRP timers versus BFD, then create one-way loss and record interface, BFD, adjacency, RIB and FIB state.

2. Cisco — PBR Recursive Next Hop

Official • IOS XE IP Routing • updated April 21, 2026
Source: https://www.cisco.com/c/en/us/td/docs/routers/ios-xe/ip-routing/b-ip-routing/m_iri-pbr-rec-next-hop-support.html

Beginner foundation — terms you need before this lesson. Policy-Based Routing (PBR) can choose forwarding based on policy rather than only destination. A recursive next hop is not directly connected; another route must first resolve how to reach it. CEF is Cisco’s forwarding information architecture.

Why it exists: recursive PBR lets policy point to a stable logical address while routing decides the current physical path toward that address. This reduces coupling between policy and one interface.

Packet sequence: ingress packet → route-map match → recursive target → RIB lookup for target → CEF adjacency resolution → hardware forwarding. Cisco documents that if equal-cost routes exist but some adjacencies are unresolved, load sharing is restricted to usable adjacencies. If recursive resolution is unavailable, default-route behavior can apply.

set next-hop recursive <ip>
show ip route <recursive-next-hop>
show ip cef <recursive-next-hop>

The route command proves the RIB knows how to reach the recursive address; CEF proves forwarding-ready adjacency. A route-map match alone does not prove the desired egress is programmed. This is a reusable troubleshooting rule for BGP, overlays and PBR: always follow the next-hop dependency one layer lower.

Lab: use two equal-cost routes to the recursive target, break one adjacency without deleting the route, and compare policy counters, RIB, CEF and packet egress.

3. Cisco — MPLS L3VPN Services Using Segment Routing

Official • Cisco 8000 / IOS XR • updated June 17, 2026
Source: https://www.cisco.com/c/en/us/td/docs/iosxr/cisco8000/l3vpn/l3vpn-config-cisco8000/mpls-l3vpn-fundamentals-and-core-deployment-w/mpls-l3vpn-services-using-segment-routing.html

Beginner foundation — terms you need before this lesson. MPLS L3VPN separates customer routes into VRFs. MP-BGP distributes VPN routes. Segment Routing over MPLS uses IGP/BGP extensions to advertise label instructions called SIDs, so a separate LDP transport-label protocol is not required.

Two independent control planes must meet. Customer prefixes enter a PE VRF and MP-BGP attaches RD/RT attributes. Separately, the IGP advertises Segment Routing reachability and Prefix-SIDs for infrastructure loopbacks. The ingress PE must resolve the remote PE’s VPN BGP next hop through that SR transport.

Packet sequence: CE packet → VRF lookup → VPN route → recursive remote-PE next hop → SR transport label + VPN/service label → P routers process SR label → egress PE uses VPN label to select VRF → CE forwarding.

show bgp vpnv4 unicast
show route <remote-PE-loopback>
show mpls forwarding

A VPN route can exist while forwarding fails because the remote PE loopback or Prefix-SID is not resolvable. Troubleshoot CE route → VRF → VPN BGP → next-hop recursion → SR label programming → core MTU → egress VRF.

Lab: remove only the SR reachability to the remote PE while keeping MP-BGP established and observe the surviving control-plane state.

4. Palo Alto Networks — Advanced Routing Engine Architecture

Official • PAN-OS Advanced Routing
Source: https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing

Beginner foundation — terms you need before this lesson. A logical router is a PAN-OS routing instance. Protocol tables contain learned candidates; the RIB chooses active routes; the FIB is forwarding-ready state. Security policy and NAT are separate from routing policy.

The Advanced Routing Engine supports static routes, BGP/MP-BGP, OSPFv2/v3, RIPv2, BFD, redistribution and route filtering. The operational lesson is to separate protocol state from selected route state and selected route state from forwarding state.

State sequence: protocol learns route → import/filter policy → candidate RIB → global route preference/next-hop validation → active route → FIB. A healthy BGP session proves only the TCP/BGP control relationship. It does not prove a route was accepted, selected, or installed.

Use More Runtime Stats → Route Table to ask what the routing system selected, then Forwarding Table to ask what can actually forward. PAN-OS documentation also notes an ECMP restriction when equal-cost routes use a virtual/logical router as next hop: such routes are not installed in FIB.

If the FIB is correct but traffic still fails, move to PAN-OS session, security policy, NAT and packet capture evidence rather than continuing to tune routing.

5. Palo Alto Networks — OSPFv2 on Advanced Routing Engine

Official • PAN-OS Advanced Routing
Source: https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing/configure-ospfv2-on-an-advanced-routing-engine

Beginner foundation — terms you need before this lesson. OSPF is a link-state IGP. Routers flood LSAs, build an LSDB and run SPF. Areas limit flooding. An ASBR injects external routes. OSPFv2 carries IPv4.

Enable OSPF, choose a unique router ID, create areas, bind interfaces and optionally attach BFD and redistribution profiles. Neighbors must agree on key parameters before reaching Full. Once Full, LSAs populate the LSDB and SPF creates route candidates.

What each layer proves: neighbor Full proves adjacency and database exchange; an LSA proves topology/external information exists; a route in the RIB proves selection; a FIB entry proves forwarding programming. Never collapse these into one “OSPF is up” statement.

For BFD, a profile can accelerate failure detection. For redistribution, a profile controls which static, connected, RIPv2, BGP or default routes become OSPF externals. That is also the place where route ownership and loop prevention must be designed.

Lab: separately break adjacency authentication and redistribution policy. Compare neighbor, LSDB and RIB evidence so you can recognize two faults that both appear as “remote prefix missing.”

6. Palo Alto Networks — Filters for the Advanced Routing Engine

Official • PAN-OS Advanced Routing
Source: https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing/create-filters-for-the-advanced-routing-engine

Beginner foundation — terms you need before this lesson. Prefix lists match destination prefixes. AS-path and community lists match BGP attributes. Route maps combine match conditions and actions. Import means entering local routing; export means advertising outward.

Routing policy is not firewall packet policy. It controls routing information: what enters the RIB, what is advertised, what is redistributed and which path attributes are modified. Palo Alto documents access lists, prefix lists, route maps, AS-path lists and community lists across the Advanced Routing Engine.

Policy sequence: receive candidate → evaluate peer/group policy → match list → permit/deny/modify → candidate RIB → best-path and next-hop validation → active route. On export, an active/eligible route is evaluated again before advertisement.

A peer can be Established while zero useful routes enter the RIB because policy rejects them. The correct troubleshooting order is peer state → received route → policy match → candidate RIB → selected RIB → FIB.

Lab: attach a correct route map in the wrong direction. Use runtime state to distinguish “never received,” “received then denied,” and “accepted but not selected.”

7. Fortinet — Bidirectional Forwarding Detection

Official • FortiGate / FortiOS 7.6.6
Source: https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/771813/bfd

Beginner foundation — terms you need before this lesson. BFD is a fast liveliness protocol. Routing protocols register as clients. A discriminator identifies the BFD session. One-way failure can be detected even when interface carrier remains up.

FortiGate can enable BFD globally, per interface or at protocol level, with lower-level settings overriding upper levels. OSPF and BGP can register for BFD events. Fortinet documents commands to compare OSPF neighbors with BFD neighbors and to see registered protocols.

get router info bfd neighbor detail
get router info bfd requests
diagnose debug application bfdd <level>

The detail command asks whether the BFD session itself is Up and which protocols registered. Requests show whether routing daemons asked BFD to create sessions. Debug is the last resort when state-machine transitions are unclear.

Fortinet explicitly notes that BFD echo mode and authentication are not supported on FortiGate in this documentation. That matters in multivendor designs: do not configure a peer to require a mode the FortiGate cannot negotiate.

Lab: enable BFD for OSPF and BGP to the same peer, introduce one-way packet loss, and compare which control protocols react.

8. Fortinet — Dynamic Routing and On-Demand Routing Daemons

Official • FortiGate / FortiOS 7.6.6
Source: https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/479509

Beginner foundation — terms you need before this lesson. A routing daemon is a process implementing a routing protocol. FortiOS uses processes such as bgpd, ospfd, isisd, ripd and ripngd. The forwarding plane does not consult these daemons for every packet.

Fortinet documents that from 7.6.5, smaller-memory FortiGate models optimize memory by starting routing daemons only when routing configuration requires them. This is operationally important because “daemon not running” can be correct when no protocol is configured.

diagnose sys top
get router info routing-table all

The first asks which processes are alive. The second asks which routes won global selection. Protocol codes distinguish BGP, OSPF, RIP and IS-IS. If a daemon is active but no adjacency forms, move to interface/VRF/VDOM and neighbor state. If the route exists but wrong protocol wins, compare administrative distance and metric.

When VDOMs are enabled, routing commands must be executed in the correct VDOM. A technically correct command in the wrong VDOM can create a false “route missing” diagnosis.

9. Fortinet — Static & Dynamic Routing Monitor

Official • FortiGate / FortiOS 7.6.6
Source: https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/655407/static-dynamic-routing-monitor

Beginner foundation — terms you need before this lesson. Route codes identify route sources. A route lookup applies longest-prefix match and current selected state. A policy route is a separate policy-driven forwarding decision that can override normal destination routing for matching traffic.

The routing monitor exposes the global routing table, policy routes, BGP neighbors/paths and OSPF neighbors. This is valuable because it separates “protocol knows about a path” from “the global routing table selected it.”

get route info routing-table all

If a BGP path is visible but not in the global route table, investigate next-hop resolution, administrative distance and competing protocols. If the correct global route is present but traffic uses another egress, inspect policy routes before assuming the routing table is wrong.

10. Arista — EOS 4.36 Routing Protocols

Official • EOS 4.36.0F
Source: https://www.arista.com/ko/um-eos/eos-routing-protocols

Beginner foundation — terms you need before this lesson. EOS exposes RIP, OSPFv2/v3, IS-IS, BGP and BFD as routing/control functions. A route map is policy applied to routing information. Maintenance mode is used to drain or alter routing during planned work.

The key beginner lesson is that each protocol can have a valid best route while the global routing table still chooses a different protocol. Always distinguish protocol best path from active route and active route from hardware forwarding.

show ip route
show ipv6 route
show bfd peers

Use the routing table to identify selected routes and their source. Use BFD only when a routing adjacency is configured as a BFD client; BFD Up is liveliness evidence, not route-policy evidence.

In a multi-protocol environment, compare route preference/administrative distance before changing protocol metrics. Metrics normally compare paths inside one protocol; administrative preference compares different route sources.

11. Arista — IS-IS, BFD and Segment Routing

Official • EOS User Manual
Source: https://www.arista.com/assets/data/pdf/user-manual/um-books/EOS-User-Manual.pdf

Beginner foundation — terms you need before this lesson. IS-IS is a link-state IGP. Level-1 and Level-2 divide routing scope. Segment Routing advertises SIDs through IS-IS. Node/Prefix SIDs represent ECMP-aware shortest paths; adjacency SIDs represent specific links.

IS-IS forms adjacency, floods LSPs and computes SPF. Segment Routing extensions add SIDs to that same topology information. EOS then programs MPLS forwarding state from the computed path and SID database. BFD can be enabled on IS-IS interfaces for faster failure detection.

router isis <instance>
 address-family ipv4
  bfd all-interfaces
interface Ethernet5/6
 isis bfd

If ordinary IS-IS IP reachability works while labeled traffic fails, the fault is likely after SPF: SID advertisement, SRGB, MPLS label programming or dataplane capability. Do not tear down a healthy IS-IS adjacency to fix a missing MPLS FIB entry.

12. Arista — BGP Nexthop Resolution RIB Profiles

Official TOI • EOS multi-agent routing • feature updated March 7, 2025
Source: https://www.arista.com/en/support/toi/tag/route-map

Beginner foundation — terms you need before this lesson. A BGP next hop is the forwarding dependency carried with a BGP route. A resolution RIB is the table/domain BGP is allowed to consult to reach that next hop. Modern services may have IP and tunnel RIBs.

This feature makes next-hop resolution policy explicit for IP unicast, L3VPN and EVPN services. The route can be the best BGP path but remain unusable if its next hop is not resolvable through an allowed RIB domain.

State sequence: BGP path accepted → BGP best path → next-hop resolution profile → selected transport RIB → resolved forwarding object → global forwarding programming.

show ip bgp <prefix>
show ip route <next-hop>

When BGP shows best but forwarding is missing, investigate the next-hop resolution domain before changing local preference, MED or AS path. Path attributes cannot repair an unreachable transport dependency.

13. FRRouting — RIP, BFD and Redistribution

Official project documentation • FRR latest
Source: https://docs.frrouting.org/en/latest/ripd.html

Beginner foundation — terms you need before this lesson. RIP is a distance-vector IGP using hop count. Metric 16 means unreachable. Split horizon avoids advertising a learned route back out the incoming interface; poison reverse advertises it back as unreachable. zebra is FRR’s routing manager.

FRR sends RIPv2 by default and can accept both v1/v2. Documentation strongly encourages disabling RIPv1 because it lacks authentication and classless prefix support. FRR RIP also supports BFD for faster peer-failure detection and route maps for redistribution.

show ip rip status
show ip rip
ip rip bfd
redistribute ospf route-map <name>

RIP route timers and metric state explain convergence; BFD changes detection speed, not RIP’s distance-vector algorithm. A redistributed route needs an explicit metric and policy model, especially if another boundary could send it back toward its source.

FRR documentation highlights route-map behavior differences versus Cisco RIP. This is a major multivendor lesson: similar CLI words do not guarantee identical policy timing/semantics.

14. FRRouting — IS-IS Segment Routing

Official project documentation • FRR stable 10.0
Source: https://docs.frrouting.org/en/stable-10.0/isisd.html

Beginner foundation — terms you need before this lesson. SRGB is the Segment Routing Global Block used for Prefix-SID labels. MSD is maximum SID/label-stack depth. Linux MPLS support is part of the FRR dataplane path.
segment-routing on

15. FRRouting — Zebra: The RIB-to-FIB Boundary

Official project documentation • FRR latest
Source: https://docs.frrouting.org/en/latest/zebra.html

Beginner foundation — terms you need before this lesson. Protocol daemons such as bgpd and ospfd send candidates to zebra. Zebra chooses across protocols and programs the OS kernel using Netlink on Linux. A route can therefore exist in a protocol table, zebra RIB and kernel FIB as three separate states.

State chain: protocol best route → zebra candidate → zebra global selection → FIB programming → kernel/hardware forwarding. FRR route output uses `>` for selected and `*` for FIB-installed in relevant displays.

show ip route <prefix>
show ip route failed
ip route show <prefix>

`show ip route failed` is especially useful because it isolates FIB installation problems. If bgpd has the path but zebra does not, inspect protocol policy/ZAPI. If zebra selects it but the FIB fails, inspect kernel/offload programming. If the kernel route exists but packets fail, move to neighbor resolution, interface, ACL, namespace or hardware dataplane.

On systems with an external hardware fast path, an FPM/offload stage can exist beyond the kernel. Identify the actual forwarding authority before declaring success.

16. Juniper — Segment Routing Concepts

Official • Junos OS
Source: https://www.juniper.net/documentation/us/en/software/junos/segment-routing/topics/concept/what-is-segment-routing-spring.html

Beginner foundation — terms you need before this lesson. A segment is a forwarding instruction. SR-MPLS encodes it as an MPLS label; SRv6 encodes it as an IPv6 SID. Prefix/Node SIDs usually follow shortest path; adjacency SIDs force a specific link.

Segment Routing advertises segments through existing IS-IS, OSPF or BGP extensions rather than requiring a separate path-signaling protocol. Every SR-enabled device learns advertised segments; a headend then chooses a segment list.

Packet model: ingress imposes segment list → each transit node processes the active instruction → labels/SIDs advance → egress removes SR transport and delivers to service/native forwarding. This is source-routed intent, but intermediate nodes still need correct IGP and FIB state.

If the segment database is missing, troubleshoot IGP/BGP advertisement. If the database is correct but traffic fails, inspect label/SID programming, stack depth and platform dataplane capability.

17. Juniper — Route Preference and BGP Path Selection

Official • Junos OS
Source: https://www.juniper.net/documentation/us/en/software/junos/bgp/topics/topic-map/bgp-overview.html

Beginner foundation — terms you need before this lesson. Junos route preference compares different route sources; lower wins. BGP LOCAL_PREF compares BGP paths; higher wins. These values live at different decision layers.

Junos BGP path selection first requires a resolvable next hop. A BGP best path can then still lose global route selection to another protocol with lower route preference. This distinction explains many “BGP says best but traffic uses static/OSPF” cases.

show bgp summary
show route <prefix> detail
show route protocol bgp

Established proves the session. `show route detail` exposes active/inactive state, route preference and next-hop clues. Junos default BGP route preference is 170, while LOCAL_PREF conventionally defaults to 100 for BGP path advertisement behavior; never compare those numbers directly.

19. Aruba/HPE — AOS-CX 10.13 OSPF Redistribution

Official • AOS-CX 10.13 IP Routing Guide / 8400
Source: https://www.arubanetworks.com/techdocs/AOS-CX/10.13/PDF/ip_route_8400.pdf

Beginner foundation — terms you need before this lesson. An ASBR injects external routes into OSPF. A route map filters candidates. Redistribution copies routes from BGP, connected, static, RIP or another OSPF process into OSPF.
router ospf 1
 redistribute bgp route-map BGP_routes

route-redistribute active-routes-only

The `active-routes-only` concept is particularly important: it can limit redistribution to routes that are actually selected for forwarding, reducing the chance of re-originating inactive alternatives. 21. Aruba/HPE — VSX Fundamentals

Official • AOS-CX 10.13 VSX Guide • published June 2024
Source: https://www.arubanetworks.com/techdocs/AOS-CX/10.13/PDF/vsx.pdf

Beginner foundation — terms you need before this lesson. VSX is Aruba’s two-switch multichassis design. The ISL links the peers. Keepalive checks peer health through a separate path. Active Gateway provides a shared first-hop gateway identity. VSX keeps separate control planes, unlike a single-control-plane stack.

Downstream servers/switches can form LACP across both VSX peers. Selected configuration/state synchronizes between peers while each switch retains independent routing/control functions. That independence improves failure isolation but requires operators to verify both peers, not assume a single logical state.

show vsx status
show lacp interfaces
show ip route
show arp

If one member path blackholes, separate LACP state, VLAN consistency, active-gateway state, ISL/keepalive health and routing/neighbor state. “VSX up” does not prove every SVI/VLAN is symmetric.

Lab: dual-home a server, then separately fail an access member, one VSX peer and the ISL. Record LACP, VSX, gateway, RIB/FIB and traffic behavior for each event.

Redistribution loop-prevention library

Rule 1: identify route ownership before redistribution. Rule 2: tag routes when they cross a protocol boundary. Rule 3: reject your own tag if the route returns at another boundary. Rule 4: use explicit prefix policy and metrics rather than blanket redistribution. Rule 5: verify the active route source before redistributing. Rule 6: test failure and recovery; loops often appear only when the primary path disappears.

Underlay / next-hop troubleshooting decision tree

  1. Does the protocol show the route/endpoint?
  2. Did import policy accept it?
  3. Is it selected in the RIB?
  4. Is the protocol/overlay next hop recursively reachable?
  5. Is the resolved adjacency/tunnel programmed in FIB?
  6. Can the outer/transport packet cross the underlay with correct MTU?
  7. Does the egress device have neighbor/service state?
  8. Does the return path resolve through the same chain?
