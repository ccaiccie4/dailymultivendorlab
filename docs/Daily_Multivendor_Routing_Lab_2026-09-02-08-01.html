Networking Foundations Primer

The mental model used throughout is learn/originate → policy → advertise/import → RIB selection → recursive next-hop resolution → FIB/adjacency/label/tunnel programming → packet forwarding → egress and return-path proof. A healthy state on the left never automatically proves the state immediately to its right.

Control plane vs data plane

The control plane exchanges protocol information and chooses reachability. The data plane is the ASIC/kernel/PFE/forwarding agent that moves packets. An Established BGP session or Full OSPF neighbor does not prove a usable FIB entry.

Route, prefix, next hop

A prefix is a destination range. A route is one candidate path to it. The next hop is the immediate or logical forwarding target. BGP next hops frequently require another route lookup before they can be used.

RIB and FIB

The Routing Information Base stores candidates and the selected route. The Forwarding Information Base contains forwarding-ready state installed in hardware or the OS kernel.

Recursive next-hop resolution

If a route points to a non-connected next hop, the router looks up that address too, repeating until it reaches a directly usable adjacency or tunnel. Best path plus unresolved next hop is still a forwarding failure.

Administrative distance / route preference

This is the local cross-protocol choice when static, OSPF, BGP, RIP or IS-IS offer the same prefix. Cisco commonly says administrative distance; Junos says route preference. It is not BGP LOCAL_PREF.

Underlay vs overlay

The underlay reaches infrastructure addresses. VXLAN, EVPN services and many VPNs are overlays built on top. Overlay control state can survive while VTEP/PE transport recursion fails.

VXLAN/VTEP/VNI

VXLAN wraps tenant traffic in UDP/IP. A VTEP adds/removes the header. A VNI is a 24-bit service identifier. An L2VNI represents a bridge domain; an L3VNI represents a tenant routing context in symmetric IRB.

EVPN RD and RT

EVPN is a BGP family for MAC/IP/prefix information. The RD makes overlapping VPN NLRI unique. Route Targets control VRF import/export membership.

IRB and anycast gateway

Integrated Routing and Bridging combines bridging and routing in an overlay. An anycast gateway presents the same first-hop identity on multiple fabric nodes so hosts can route locally.

BUM traffic

Broadcast, unknown-unicast and multicast frames require replication or multicast transport because a single remote unicast destination is not known.

Redistribution

Redistribution re-originates routes from one routing source into another. It is a policy boundary that can create feedback loops unless origin is tagged and return redistribution is filtered.

LACP and multichassis

LACP bundles links. MLAG, vPC, VSX and MC-LAG coordinate two switches for one logical attachment. EVPN multihoming solves a related redundancy problem using Ethernet-Segment signaling.

ESI and DF

An Ethernet Segment Identifier identifies a multihomed segment. Designated Forwarder election controls which PE/VTEP forwards certain BUM traffic toward it.

VRF, VLAN and trunk

A VRF is a separate Layer-3 routing context. A VLAN is a Layer-2 broadcast domain. A trunk carries multiple VLANs over one link.

1. Cisco — BGP Diverse Path Using a Diverse-Path Route Reflector

Platform: IOS XE 17.x · Source: official configuration guide

https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-routing/b-ip-routing/m_irg_diverse_path.html

Beginner foundation — terms you need before this lesson

A route reflector removes the need for a full iBGP mesh, but normally reflects only the path it selects. A diverse path is an intentionally retained and advertised second path. A shadow RR is an RR used to compute/advertise that alternate.

Why and topology

RRs can hide real egress diversity from clients. Cisco’s feature preserves one additional path inside one RR cluster so clients know an alternate before the preferred exit fails. Use two egress PEs and an RR/shadow-RR plane that receives equivalent BGP inputs.

Control and packet sequence

PEs advertise multiple paths → normal RR selects best → diverse-path computation selects backup, best-external or multipath → client learns best plus alternate → RIB/CEF can retain/install the alternate. User packets still follow the selected FIB; “two BGP paths” are useful only if their recursive next hops traverse different failure domains.

Command teaching

bgp additional-paths select backup calculates a backup. bgp additional-paths install asks for RIB/CEF installation. neighbor <ip> advertise diverse-path backup sends it to a client. show ip bgp neighbor <ip> advertised-routes proves what was sent, not whether the receiver programmed forwarding.

Troubleshooting, caveats and lab

If a client still learns one exit, prove the RR calculated a second path, the client is eligible to receive it, and IGP metric handling is consistent. Cisco limits the design to a single cluster and one additional plane. Lab two egress PEs and fail only the best exit while measuring whether the client already has a forwarding-ready alternate.

2. Cisco — BGP Multiple Sourced Paths Per Redistributed Route

Platform: IOS XE 17.x · Source: official configuration guide

https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-routing/b-ip-routing/m_bgp_multi_paths_redistribute.html

Beginner foundation — terms you need before this lesson

A sourced BGP route is injected locally with redistribution or a network statement rather than learned from a peer. This feature allows more than one distinct gateway for that locally sourced prefix to survive into BGP.

Why and topology

Without sourced multipath, several useful RIB paths can collapse into a single BGP-origin path. Start with one prefix that has multiple distinct gateways in the RIB, then source it into BGP.

Control and packet sequence

RIB holds several candidates → sourcing policy admits them → BGP creates local path objects → multipath/path selection decides installation/export → FIB still requires each gateway to resolve. Cisco documents that 0.0.0.0 gateway paths do not gain this multipath behavior and each sourced path must have a unique gateway.

Command teaching

show ip route <prefix> proves distinct gateways exist before BGP. show ip bgp <prefix> shows locally sourced BGP paths. If redistribution is missing, verify route-map/source eligibility and gateway form before touching LOCAL_PREF/MED.

Troubleshooting, caveats and lab

Cisco notes possible inconsistency when a manual static route and an RRI-inserted route use different tags for the same prefix. Normalize route ownership/tags first. Lab two static next hops, source them into BGP, then change one source form and compare RIB/BGP/FIB.

3. Cisco — MPLS Traffic Engineering Fast Reroute Link and Node Protection

Platform: IOS XE 17.x · Source: official MPLS guide

https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/mpls/b-mpls/m_mp-te-frr-node-prot-0.html

Beginner foundation — terms you need before this lesson

An MPLS-TE LSP is a traffic-engineered label path. FRR pre-establishes a backup tunnel. Link protection bypasses one link; node protection bypasses the next-hop node.

Why and topology

FRR keeps traffic moving locally while RSVP-TE and the IGP reconverge. A primary tunnel crosses a protected resource and a next-hop or next-next-hop backup tunnel goes around it.

Control and packet sequence

IGP/TE database → RSVP primary LSP → backup LSP → association with protected interface → FRR database Ready. On failure, the local label rewrite immediately sends packets into the backup before global convergence finishes.

Command teaching

tunnel mpls traffic-eng fast-reroute makes the primary eligible for protection. show mpls traffic-eng fast-reroute database asks whether protection is Ready, Active or Partial. “Configured” is not “protected”; the backup must be established and correctly associated.

Troubleshooting, caveats and lab

If a TE tunnel is Up but traffic drops on failure, verify FRR was Ready before failure and that the backup really bypasses the failed link/node. Cisco states backup tunnels themselves are not protected by this mechanism. Build a four-node square and fail the protected resource while watching labels and loss.

4. Palo Alto Networks — Static Route Path Monitoring

Platform: Advanced Routing Engine · Source: current official docs

https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing/create-a-static-route

Beginner foundation — terms you need before this lesson

A static route normally remains installed while local next-hop conditions are valid. Path monitoring actively probes one or more remote destinations and can remove the route from both RIB and FIB when the path fails.

Why and topology

An interface can stay Up while an upstream path is unusable. Configure a primary and lower-preference backup route, then monitor reliable targets beyond the local link. Any versus All failure logic determines how many targets must fail.

Control and packet sequence

Primary static route is eligible → monitor probes run → failure threshold reached → primary is removed from RIB/FIB → backup wins → recovery plus preemptive hold allows primary reinstall. User packets follow the current FIB; monitor probes are only health evidence.

Command teaching

show advanced-routing static-route-path-monitor proves monitor state. Runtime Route Table proves RIB selection; Forwarding Table proves FIB. A healthy monitor still does not prove security/NAT permits the application.

Troubleshooting, caveats and lab

If the route flaps when one endpoint is maintained, review Any/All and probe-target reliability. PAN-OS supports monitoring up to 128 static routes in the cited workflow. Lab two defaults, two targets, Any/All logic and preemptive hold timing.

5. Palo Alto Networks — BGP Graceful Restart

Platform: Advanced Routing Engine · Source: current official docs

https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing/configure-bgp-on-an-advanced-routing-engine

Beginner foundation — terms you need before this lesson

BGP GR lets a helper temporarily retain routes from a restarting peer as stale instead of immediately withdrawing them. It assumes forwarding may remain valid while control state rebuilds.

Why and topology

Short control-plane restarts otherwise cause large route churn. PAN-OS exposes Stale Route Time, Local Restart Time and Max Peer Restart Time.

Control and packet sequence

GR capability is negotiated → peer restarts → helper retains eligible stale routes → dataplane can continue → peer re-establishes and refreshes RIB → stale state clears, or timers expire and routes are removed.

Command teaching

Pair BGP neighbor/session state with route and forwarding tables. An Established peer after restart does not prove all stale routes were refreshed. GR configuration proves policy, not that the restarting peer truly preserved forwarding.

Troubleshooting, caveats and lab

A blackhole during GR often means the helper retained a route whose next hop/dataplane was not actually valid. Current docs cite 120-second defaults for key timers. Lab a control-only restart, then repeat with forwarding loss and compare packet outcome.

6. Palo Alto Networks — OSPF Graceful Restart and Strict LSA Checking

Platform: Advanced Routing Engine · Source: current official docs

https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing/configure-ospfv2-on-an-advanced-routing-engine

Beginner foundation — terms you need before this lesson

OSPF helpers can preserve routes while a neighbor restarts. Strict LSA checking makes the helper stop if topology changes make the pre-restart view unsafe.

Why and sequence

Restarting router signals grace → helper retains assumptions → adjacency/LSDB rebuild → stable topology permits a graceful return; relevant LSA change can abort helping. Forwarding can continue on the old FIB only while that state remains valid.

Command teaching

Check neighbor state, LSDB and global RIB separately. Helper state explains why routes are retained; it does not prove the restarting firewall is forwarding. Align GR hello delay/dead timers and grace windows.

Troubleshooting, caveats and lab

If adjacency drops during HA restart, check hello delay versus dead timer and helper capability. If helper exits immediately, look for topology-changing LSAs under strict checking. Lab a stable restart and then a restart while a transit link changes.

8. Fortinet — OSPF Link Detection Customization

https://docs.fortinet.com/document/fortigate/8.0.0/administration-guide/204475/ospf-link-detection-customization

Beginner foundation — terms you need before this lesson

Convergence begins with failure detection. FortiOS can notify OSPF immediately when the lower physical link behind a documented VLAN interface goes Down, instead of waiting for a slower notification path.

Control and packet sequence

9. Fortinet — Dynamic BGP Versus Route Reflection in ADVPN

Platform: FortiOS 7.6 architecture · Source: official design docs

https://docs.fortinet.com/document/fortigate/7.6.0/sd-wan-architecture-for-enterprise/804958/dynamic-bgp-versus-route-reflection

Beginner foundation — terms you need before this lesson

Route reflection has the hub re-advertise spoke routes. Dynamic BGP forms spoke-to-spoke BGP over ADVPN shortcuts so route exchange can move away from the hub.

Why and sequence

Traditional: spokes → hub RR → other spokes. Dynamic design: shortcut forms → spoke-to-spoke BGP session forms → routes exchange directly → RIB recursively resolves across the shortcut → SD-WAN forwarding can use it. This reduces hub control-plane scale.

Command teaching

Use BGP neighbor/path views together with ADVPN tunnel and SD-WAN state. BGP Established across a shortcut does not prove the shortcut is selected by the RIB or SD-WAN policy.

Troubleshooting, caveats and lab

If traffic still hairpins, inspect route next hops and SD-WAN steering before blaming BGP. Fortinet documents BGP over loopback as required for ADVPN 2.0. Compare reflected versus dynamic route next hops in a two-spoke lab.

No stable direct raster URL was verified; no image URL is invented. Source article.

10. Arista — Dynamic BGP Neighbors and Listen Ranges

Platform: EOS 4.36 · Source: official user manual

https://www.arista.com/en/um-eos/eos-border-gateway-protocol-bgp?tmpl=component

Beginner foundation — terms you need before this lesson

A static neighbor names one exact peer. A dynamic neighbor is accepted from a configured address range and inherits a dynamic peer-group policy.

Why and sequence

Scale-out fabrics can avoid repetitive peer statements. Incoming TCP/179 from the listen range → EOS associates it with the peer group → BGP Open validates AS policy → session establishes → routes exchange under inherited policy.

Command teaching

bgp listen range <prefix> peer-group <name> remote-as <asn> defines the acceptance range. show ip bgp neighbors <ip> shows live neighbor state and inherited group. Established does not prove routes passed route-map policy.

Troubleshooting, caveats and lab

An unexpectedly accepted peer means the range/AS controls are too broad. An intended peer that fails must source from the expected address and satisfy group AS rules. Dynamic peers are group-configured rather than individually customized. Lab two accepted peers and one out-of-range peer.

11. Arista — VARP Active-Active First-Hop Gateway

Platform: EOS / ATD 2026.2 · Source: Arista lab guide

https://labguides.testdrive.arista.com/2026.2/data_center/l3ls-bgp/

Beginner foundation — terms you need before this lesson

VARP lets multiple switches route for the same virtual gateway IP and common virtual MAC simultaneously. Unlike active/standby VRRP, either leaf can route locally.

Why and packet sequence

Host ARPs for shared gateway → local leaf answers with shared virtual MAC → host sends frame → receiving leaf performs local L3 lookup → northbound RIB/FIB selects path. The first-hop identity is shared; the routing control planes remain independent.

Command teaching

Arista’s current lab uses ip virtual-router mac-address 00:1c:73:00:00:34, ip virtual-router address 10.111.134.1, and show ip virtual-router. Up VARP proves first-hop state, not northbound reachability.

Troubleshooting, caveats and lab

If only one leaf forwards, compare SVI/VLAN consistency, virtual IP/MAC, MLAG and each leaf RIB/FIB. Lab remove the northbound route on one leaf while keeping VARP active to prove gateway health and routed reachability are separate.

12. Arista — IS-IS Graceful Restart

Control and packet sequence

13. FRRouting — LDP from Label Mapping to Kernel MPLS State

Platform: FRR latest · Source: official FRR docs

https://docs.frrouting.org/en/latest/ldpd.html

Beginner foundation — terms you need before this lesson

LDP exchanges MPLS label bindings. FRR’s ldpd owns LDP protocol state, zebra stores MPLS information, and the kernel is the forwarding layer.

Why and sequence

IGP makes transport addresses reachable → LDP discovers peers and opens a session → label mappings exchange → zebra receives MPLS state → Linux/OpenBSD forwarding is programmed. Packets push/swap/pop labels according to the dataplane table.

21. Aruba/HPE — BGP Community Lists and Route Maps in New Central

Platform: HPE Aruba Networking Central API · Source: official API docs

https://developer.arubanetworks.com/new-central-config/reference/readroutemaps

Beginner foundation — terms you need before this lesson

A BGP community is a route tag. Community lists match tags. Route maps combine match conditions with permit/deny and set actions for import, export and redistribution policy.

Control sequence

Route reaches policy attachment → route-map sequences evaluate → match selects prefix/community/AS path → permit/deny/set action executes → accepted route enters RIB or advertisement pipeline. A route map is routing policy, not a packet firewall ACL.

Command/API teaching

Central’s GET .../route-maps reads route-map configuration. Community-list APIs document Standard, Expanded and Extended types, including route-target values. HTTP/API success proves the object exists, not that a BGP peer actually evaluated it.

Troubleshooting, caveats and lab

If an expected community is absent, verify sequence order, attachment direction, object type and received/advertised route evidence. Automation can replicate a bad policy widely, so validate scope and dependencies before rollout. Lab mark one prefix and confirm the peer receives only the intended attribute change.

Redistribution-loop library

Protocol A → redistribute into Protocol B at boundary 1 → later redistribute B back into A at boundary 2 is a classic feedback pattern. Mark route origin with tags/communities, filter the return direction, document ownership, and decide whether only active routes are eligible. Administrative distance may hide a feedback route without eliminating the mechanism.

Evidence-first troubleshooting decision tree

  1. Physical/L2: interface, LACP, VLAN, MTU.
  2. Neighbor/session: hello, TCP, BFD, LDP, OSPF, IS-IS, BGP.
  3. Protocol database: LSDB, BGP RIB, label bindings, EVPN routes.
  4. Policy: route maps, prefix/community lists, RT import/export, redistribution filters.
  5. Global RIB: did the candidate win AD/preference and metric?
  6. Recursive next hop: can every next-hop/VTEP/label dependency resolve?
  7. FIB/dataplane: CEF, kernel, PFE, forwarding agent, label/tunnel state.
  8. Packet evidence: counters, capture, MTU, security policy, egress and return path.

L2-over-L3, MPLS, EVPN/VXLAN and SD-Access refresher

VXLAN depends on VTEP underlay reachability; MPLS depends on label state plus IGP transport; SD-Access uses LISP for endpoint/control mapping and VXLAN for data transport. Across all three, separate service control state from transport recursion and from forwarding programming.
