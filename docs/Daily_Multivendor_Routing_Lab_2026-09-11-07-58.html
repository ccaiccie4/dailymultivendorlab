Networking Foundations Primer

Universal state chain: learn/originate → policy → advertise/import → RIB selection → recursive next-hop resolution → FIB/adjacency/tunnel/label programming → forwarding → delivery → return path.

Control plane vs data plane

The control plane exchanges topology, reachability, labels, endpoint mappings and policy. The data plane is the FIB, adjacency, tunnel, label stack, ECMP object or ASIC/kernel state that forwards packets.

Route / prefix / next hop

A prefix names a destination range. A route is a candidate path to it. A next hop is the immediate or recursively resolved forwarding target.

RIB / FIB / adjacency

The RIB stores and selects candidates. The FIB is forwarding-ready state. An adjacency is the final neighbor/tunnel/label relationship needed to transmit.

Recursive next-hop resolution

A BGP or overlay next hop can point to another route; resolution continues until it reaches a usable adjacency or fails.

Route origin and preference

A route's origin describes where it came from. Administrative distance/route preference chooses among different routing sources before forwarding is programmed.

Underlay / overlay

The underlay reaches infrastructure endpoints. VXLAN, EVPN and MPLS overlays build tenant/service forwarding on that transport.

VXLAN / VTEP / VNI

VXLAN wraps tenant traffic in UDP/IP. VTEPs encapsulate/decapsulate. VNIs identify logical Layer-2 or Layer-3 services.

EVPN / route types / RD / RT

EVPN uses BGP for MAC/IP/prefix/service signaling. RD makes VPN NLRIs unique; RT controls VPN import/export membership.

IRB / symmetric vs asymmetric IRB

IRB joins bridging and routing. Symmetric IRB routes both directions through tenant VRFs/L3VNI; asymmetric IRB can bridge one side and route at the local ingress/egress VTEPs.

Anycast gateway

Multiple fabric nodes present the same first-hop IP/MAC so hosts keep a local gateway after mobility.

BUM

Broadcast, unknown-unicast and multicast traffic must be replicated or multicast because a single known remote unicast destination is absent.

Redistribution / tags / policy

Redistribution re-originates routes between protocols. Tags, communities, prefix lists and route maps preserve provenance and prevent feedback loops.

LACP / ESI / DF / multichassis

LACP negotiates bundles. MLAG/vPC/VSX/MC-LAG coordinate chassis; EVPN ESI identifies a multihomed segment and DF election controls selected BUM forwarding.

VRF / VLAN / trunk

A VRF is an isolated L3 routing table; a VLAN is an L2 broadcast domain; a trunk carries multiple VLANs.

1. Cisco Systems — BGP Prefix-Based Outbound Route Filtering (ORF)

Official source: https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/iproute_bgp/configuration/xe-3se/3650/irg-xe-3se-3650-book/irg-oubound-route-filtering.html

Beginner foundation — terms you need before this lesson

Outbound Route Filtering (ORF) lets a BGP receiver tell the sender which prefixes it wants before the sender transmits unwanted UPDATEs. The receiver's inbound prefix-list can effectively become filtering state at the sender.

Problem statement / why it matters

Without ORF, a provider can send a full table only for the customer to discard most of it. ORF reduces update volume, receiver CPU work and memory pressure.

Topology, architecture and state sequence

Peers establish BGP → OPEN capability negotiation advertises ORF send/receive support → receiver sends prefix-list ORF entries → sender installs them as outbound filtering state → a route-refresh/ORF immediate action causes the sender to regenerate only permitted advertisements.

Source-supported configuration and evidence

Cisco documents send/receive ORF capability per address family and a route-refresh trigger such as `clear ip bgp ... in prefix-filter`. Verify capability negotiation plus the remote ORF state; an Established session alone does not prove ORF is active.

Failure mode, remediation and reproducible lab

If the receiver is configured to send ORF but the peer never negotiated receive capability, unwanted routes continue to arrive. Lab: permit only two prefixes, compare advertised/received counts before and after ORF.

2. Cisco Systems — OSPF LSA Throttling

Official source: https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-routing/b-ip-routing/m_iro-lsa-throt-0.html

Beginner foundation — terms you need before this lesson

OSPF floods Link-State Advertisements (LSAs). During instability, repeatedly regenerating the same LSA can consume CPU and bandwidth. LSA throttling dynamically increases the delay between repeated instances while still sending the first change quickly.

Problem statement / why it matters

Fast convergence and churn protection pull in opposite directions. Adaptive throttling lets the first topology change propagate quickly but slows repeated flaps.

Topology, architecture and state sequence

Topology change occurs → first LSA is generated immediately → another change to the same LSA arrives → start/hold timer controls the next origination → repeated changes increase spacing until max wait → receiver-side arrival timer can drop overly frequent instances.

Source-supported configuration and evidence

Cisco documents `timers throttle lsa all <start> <hold> <max>` and `timers lsa arrival`. The arrival interval should not exceed the sender hold behavior in ways that cause legitimate updates to be discarded.

Failure mode, remediation and reproducible lab

A link may flap many times while neighbors see fewer LSAs because throttling is intentionally coalescing churn. Inspect LSA timestamps/sequence and throttling timers before blaming packet loss.

3. Cisco Systems — BGP Slow-Peer Detection and Update-Group Isolation

Official source: https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/iproute_bgp/configuration/xe-16-12/irg-xe-16-12-book/detecting-and-mitigating-a-bgp-slow-peer.html

Beginner foundation — terms you need before this lesson

BGP peers that share identical outbound policy are grouped so one formatted UPDATE can be reused. A persistently slow peer can hold cached messages and block faster peers from receiving new updates promptly.

Problem statement / why it matters

One congested or CPU-bound neighbor should not cause head-of-line blocking for every peer in the same update group.

Topology, architecture and state sequence

Update group formats advertisements → each peer drains cached messages → one peer falls behind for longer than the detection threshold → IOS XE marks it slow and can move it into a separate slow update group → healthy peers resume independent update formatting.

Source-supported configuration and evidence

Cisco documents `bgp slow-peer detection` and slow-peer split-update-group behavior. The default detection threshold is 300 seconds. Verify queue age and update-group membership rather than only TCP state.

Failure mode, remediation and reproducible lab

A temporary convergence burst is not necessarily a slow-peer condition. The diagnostic signature is sustained inability to consume updates, not a short post-reset queue spike.

4. Palo Alto Networks — RIPv2 Redistribution Metric Precedence

Official source: https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing/create-ripv2-routing-profiles

Beginner foundation — terms you need before this lesson

Redistribution takes routes from another source and re-originates them into RIP. PAN-OS can assign a metric in the redistribution profile, but a route-map can override that metric for matched routes.

Problem statement / why it matters

Operators need predictable metric assignment when only some redistributed routes should be made more or less attractive.

Topology, architecture and state sequence

Source-supported configuration and evidence

Failure mode, remediation and reproducible lab

5. Palo Alto Networks — IGMP Robustness and Immediate Leave

Official source: https://docs.paloaltonetworks.com/ngfw/networking/ip-multicast/configure-ip-multicast

Beginner foundation — terms you need before this lesson

IGMP tracks which receiver-facing interfaces still want multicast groups. Robustness increases tolerance for lost control packets; Immediate Leave removes the group immediately when the firewall knows there is only one member.

Problem statement / why it matters

Receiver cleanup can be either conservative or fast. Lossy segments need tolerance; single-receiver segments can reclaim multicast forwarding state immediately.

Topology, architecture and state sequence

Querier sends membership queries → receivers reply → robustness influences membership/querier timers → a receiver sends Leave → ordinary behavior sends group-specific queries and waits → Immediate Leave can remove the outgoing interface from mRIB/mFIB immediately when safe.

Source-supported configuration and evidence

PAN-OS documents Robustness 1–7, query timers, Max Groups/Sources and Immediate Leave. Immediate Leave is unavailable with IGMPv1.

Failure mode, remediation and reproducible lab

Enabling Immediate Leave on a segment with hidden multiple receivers can interrupt users behind a proxy/switch. Validate the Layer-2 receiver model before shortening leave behavior.

6. Palo Alto Networks — OSPF Graceful-Restart Hello Delay vs Dead Timer

Official source: https://docs.paloaltonetworks.com/ngfw/help/11-1/network/network-virtual-routers/ospf/ospf-areas-tab

Beginner foundation — terms you need before this lesson

During active/passive HA graceful restart, PAN-OS can send Grace LSAs for a short period while normal Hellos are intentionally delayed. The neighbor dead timer is still counting.

Problem statement / why it matters

If the grace hello-delay window is too close to or longer than neighbor dead time, the adjacency can expire even though graceful restart was intended to preserve it.

Topology, architecture and state sequence

Restart begins → firewall emits Grace LSAs at one-second intervals → ordinary Hellos pause for the configured Graceful Restart Hello Delay → neighbor dead timer continues → if Hellos resume before dead expiry, adjacency can be preserved; otherwise normal failure detection wins.

Source-supported configuration and evidence

PAN-OS documents a 1–10 second Graceful Restart Hello Delay and recommends a dead timer at least four times the hello-delay value.

Failure mode, remediation and reproducible lab

An HA failover that repeatedly drops OSPF despite GR can be a timer-design problem rather than missing Grace LSAs. Compare the hello-delay with Hello×Dead Counts.

8. Fortinet — BGP Link-Down Failover

Official source: https://docs.fortinet.com/document/fortigate/7.6.7/cli-reference/225427711/config-router-bgp

Beginner foundation — terms you need before this lesson

BGP normally detects peer failure through TCP/keepalive/hold timers. `link-down-failover` lets a neighbor react directly to an underlying interface-down event.

Problem statement / why it matters

Waiting for the BGP hold timer can be unnecessarily slow when the directly related link failure is already known locally.

Topology, architecture and state sequence

Source-supported configuration and evidence

FortiOS exposes `link-down-failover` per neighbor. Verify that the neighbor is tied to the interface/path whose carrier event you expect to trigger the reaction.

Failure mode, remediation and reproducible lab

It does not accelerate failures that leave carrier Up, such as remote blackholes; BFD or protocol timers may still be required for those cases.

10. Arista Networks — BGP Long-Lived Graceful Restart

Official source: https://www.arista.com/en/support/toi/eos-4-25-2f

Beginner foundation — terms you need before this lesson

Standard BGP Graceful Restart retains stale routes for a limited restart interval. Long-Lived Graceful Restart extends stale-route signaling/retention beyond the classic restart-time ceiling for control-plane outages where forwarding may survive longer.

Problem statement / why it matters

Large systems or planned maintenance can take longer than standard GR windows. LLGR avoids premature route withdrawal when the data plane is still valid.

Topology, architecture and state sequence

Peers negotiate GR/LLGR capability → session fails/restarts → helper marks routes stale/LLGR-stale while forwarding continues → restart/LLGR timers govern retention → refreshed routes replace stale state or timers expire and purge them.

Source-supported configuration and evidence

Arista documents BGP Long-Lived Graceful Restart in EOS 4.25.2F. Verification should inspect negotiated GR/LLGR capability and stale-path timers, not just Established state after recovery.

Failure mode, remediation and reproducible lab

Keeping stale routes too long is dangerous if the restarting node is not actually forwarding. LLGR must be paired with credible forwarding-plane preservation.

Official source: https://www.arista.com/en/support/toi/eos-4-34-0f

Peer tagging labels routes based on the peer or peer group that supplied them, then uses that tag in outbound filtering to prevent re-advertising routes back toward selected peer sets.

18. Juniper Networks — Independent-Domain Attribute-Set Tunneling

Official source: https://www.juniper.net/documentation/us/en/software/junos/cli-reference/topics/ref/statement/independent-domain-edit-routing-options.html

Beginner foundation — terms you need before this lesson

Independent-domain uses BGP Attribute Set (attribute 128) to carry another domain's BGP attributes transparently through an internal service-provider BGP core.

Problem statement / why it matters

Layer-3 VPN customers may need their AS-local BGP attributes preserved without leaking the provider's internal BGP semantics into the customer domain.

Topology, architecture and state sequence

Customer-originated BGP attributes enter PE → independent-domain wraps/tunnels them in Attribute Set → provider iBGP carries the route through core → egress restores customer-domain attributes for advertisement to the far CE.

Source-supported configuration and evidence

Junos documents `independent-domain` and optional `no-attrset`. If attribute 128 is received without an independent-domain configuration, it is treated as an unknown attribute.

Failure mode, remediation and reproducible lab

A policy that strips or mishandles Attribute Set can destroy the intended customer-domain transparency.

Official source: https://www.arubanetworks.com/techdocs/AOS-CX/10.10/PDF/ip_route_4100i-6000-6100-6200.pdf

Beginner foundation — terms you need before this lesson

AOS-CX can assign different administrative distances to OSPF intra-area, inter-area and external routes when competing against other routing protocols.

Problem statement / why it matters

Migration designs may want external OSPF routes to lose to another protocol while keeping intra-area OSPF strongly preferred.

Topology, architecture and state sequence

OSPF computes its route → route type is classified → configured route-type distance is applied → global RIB compares OSPF candidate with BGP/static/other source → winner reaches FIB.

Source-supported configuration and evidence

AOS-CX documents `distance [intra-area ...] [inter-area ...] [external ...]`. Inside OSPF, intra-area precedence remains an OSPF path-type rule; AD matters across route sources.

Failure mode, remediation and reproducible lab

Changing external OSPF distance does not alter SPF cost or convert E1/E2 behavior. It changes cross-protocol RIB preference.

Official source: https://www.arubanetworks.com/techdocs/AOS-CX/10.15/PDF/ip_route_4100i-5420-6000-6100-6200.pdf

Beginner foundation — terms you need before this lesson

BGP update groups let peers with equivalent outbound policy share formatted UPDATE work instead of independently building the same advertisements.

Problem statement / why it matters

Large peer counts can consume control-plane CPU when identical outbound routes are serialized repeatedly.

Topology, architecture and state sequence

Peers are classified by equivalent export behavior → BGP builds shared update-group state → one formatted advertisement is reused across group members → policy divergence causes peers to split into different groups.

Source-supported configuration and evidence

AOS-CX exposes an update-group enable control and operational BGP peer-group/update state in current routing documentation.

Failure mode, remediation and reproducible lab

Two peers in different route-map/community settings may not share an update group even if they are in the same configured peer group.

21. Aruba/HPE — BGP Missing MED Treated as Worst

Official source: https://developer.arubanetworks.com/aoscx/reference/post_system-vrfs-vrf-name-bgp-routers

Beginner foundation — terms you need before this lesson

BGP MED is optional. When one route lacks MED, implementations need a rule for comparison. AOS-CX exposes `bestpath_med_missing_as_worst` to treat missing MED as the largest possible value instead of the usual favorable zero-like interpretation.

Problem statement / why it matters

Mixed vendors can choose different exits if one treats missing MED as best while another treats it as worst.

Topology, architecture and state sequence

Candidate paths reach MED comparison → one path has MED and another lacks it → missing-as-worst substitutes an effectively maximum MED → the path with explicit lower MED wins, subject to all earlier best-path criteria.

Source-supported configuration and evidence

AOS-CX REST BGP router schema exposes `bestpath_med_missing_as_worst`. Verify the competing paths actually reach the MED step before expecting the knob to matter.

Failure mode, remediation and reproducible lab

The setting cannot override LOCAL_PREF or AS-path differences evaluated earlier in best-path selection.
