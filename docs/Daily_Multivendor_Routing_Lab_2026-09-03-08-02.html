Networking Foundations Primer

Universal state chain: learn/originate → policy → advertise/import → RIB selection → recursive next-hop resolution → FIB/adjacency/tunnel/label programming → packet forwarding → remote delivery → return-path proof.

Control plane vs data plane

The control plane exchanges routing, topology, membership, and policy information and decides what should be reachable. The data plane is the forwarding machinery that actually moves packets. A healthy protocol session never proves that the selected route, multicast tree, label, tunnel, or hardware entry can forward.

Route, prefix, next hop

A prefix describes a destination range. A route is one candidate path toward it. The next hop is the immediate forwarding target, or a logical address that must itself be resolved before the original route becomes usable.

RIB and FIB

The Routing Information Base (RIB) stores candidates and the selected route. The Forwarding Information Base (FIB) is the forwarding-ready representation programmed into an ASIC, PFE, forwarding agent, or operating-system kernel.

Adjacency

An adjacency is the forwarding relationship to the next device or neighbor. Depending on the technology it can mean ARP/ND resolution, an IGP neighbor, a PIM neighbor, an MPLS next hop, or an encapsulation endpoint. Always state which adjacency you are proving.

Recursive next-hop resolution

A route such as BGP may point to an address that is not directly connected. The device must perform another route lookup to reach that address, and that lookup may recurse again. The route is usable only when recursion terminates in a valid forwarding adjacency or tunnel.

Route origin and route preference

Route origin says where a route came from; preference/administrative distance decides between different routing sources locally. Cisco commonly says administrative distance; Junos says route preference. This is different from BGP LOCAL_PREF, which compares BGP paths.

Underlay vs overlay

The underlay provides transport reachability between infrastructure endpoints. An overlay provides a logical service on top. VXLAN, MPLS VPNs, EVPN, and NHRP-based shortcuts all depend on a working underlay even when their own control plane looks healthy.

VXLAN, VTEP and VNI

VXLAN encapsulates tenant traffic in UDP/IP. A VTEP adds or removes that header. The 24-bit VNI identifies the logical service. An L2VNI is a bridge domain; an L3VNI is a tenant routing context in symmetric IRB.

EVPN, RD and RT

EVPN is a BGP address family for MAC, IP and prefix reachability. A Route Distinguisher makes otherwise identical VPN routes unique. Route Targets decide which VRFs import or export them.

IRB and anycast gateway

Integrated Routing and Bridging combines Layer-2 bridging with Layer-3 routing. An anycast gateway presents the same first-hop gateway identity on multiple fabric nodes so a host can use a local gateway after movement.

BUM traffic

Broadcast, unknown-unicast and multicast traffic has no single known unicast destination. A Layer-2 overlay must therefore replicate it or use multicast transport.

Redistribution and route policy

Redistribution re-originates selected routes from one routing source into another. Prefix lists, route maps, policy-statements, tags and communities control what crosses the boundary. Native loop prevention inside one protocol does not automatically protect a multi-protocol boundary.

LACP and multichassis

LACP bundles physical links. MLAG, vPC, VSX and MC-LAG coordinate two physical switches as one logical attachment. EVPN multihoming solves a related redundancy problem with standardized Ethernet-Segment signaling.

ESI and DF

An Ethernet Segment Identifier identifies a multihomed Ethernet segment. Designated Forwarder election decides which EVPN PE/VTEP sends certain BUM traffic toward that segment so duplicate delivery is avoided.

VRF, VLAN and trunk

A VRF creates a separate Layer-3 routing table. A VLAN creates a Layer-2 broadcast domain. A trunk carries multiple VLANs over one physical or logical link.

1. Cisco Systems — EIGRP Wide Metrics

Platform/release: Cisco IOS XE 16.11 / named-mode EIGRP
Source/update: Official Cisco configuration guide; current page verified 2026-09-03

Exact source: https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/iproute_eigrp/configuration/xe-16-11/ire-xe-16-11-book/ire-wid-met.html

Beginner foundation — terms you need before this lesson

Classic EIGRP uses a composite metric built primarily from bandwidth and delay. On very fast links, the old 32-bit scale can make materially different links look equivalent. Wide metrics use a larger 64-bit calculation and RIB scaling; Cisco documents them for EIGRP named mode.

Why this feature exists

Modern Ethernet and port-channels can exceed the granularity that classic EIGRP metrics were designed around. Wide metrics exist so a 10/40/100/400-Gigabit design does not accidentally collapse different paths into the same effective metric or create unintended equal-cost forwarding.

Architecture, control-plane sequence and data-plane consequence

Interface bandwidth and delay feed the EIGRP metric calculation. In named mode, wide-metric computation creates a 64-bit value and scales it for the RIB. DUAL still chooses loop-free successors and feasible successors; the feature changes the metric precision, not EIGRP's fundamental loop-free algorithm. The operational chain is interface attributes → EIGRP metric → DUAL successor choice → RIB selection → FIB programming.

Command / GUI / API teaching

show ip eigrp topology

Asks EIGRP which successors/feasible successors and metrics it currently holds. Healthy means the intended path has the lower metric; this does not prove the interface bandwidth/delay values are correct.

show interfaces

Proves the actual interface bandwidth/delay inputs exposed to routing. An unexpectedly inherited/default delay is often the real reason for a surprising EIGRP metric.

router eigrp <name>

Enters named-mode configuration, which Cisco documents as the mode in which 64-bit wide metrics operate.

Expected versus abnormal state and evidence-first troubleshooting

A common failure is not an adjacency loss at all: two high-speed paths unexpectedly become equal cost. Compare interface delay and the topology-table metric before changing variance or route policy. If the topology metric is already wrong, load-balancing symptoms are downstream consequences.

Design, release and multivendor caveat

Cisco documents wide metrics as supporting aggregate interface speeds up to roughly 4.2 Tbps and notes that 64-bit calculations operate in named mode. Mixed classic/named deployments require deliberate metric compatibility testing.

Reproducible lab

Create 10G and 40G parallel paths with realistic delays. Observe classic-looking metric inputs, then use named-mode wide metrics and verify which path wins. Change only interface delay and predict DUAL's new successor before checking output.

Active recall: Why can two physically different high-speed paths become accidental ECMP in EIGRP, and which metric input would you verify first?

2. Cisco Systems — OSPFv3 Prefix Suppression

Platform/release: Cisco IOS XE 17.x / Catalyst 9000
Source/update: Official Cisco OSPF configuration guide; refreshed 2026

Exact source: https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-routing/b-ip-routing/m_iro-pref-supp-v3.html

Beginner foundation — terms you need before this lesson

OSPFv3 separates topology from address information more cleanly than OSPFv2. Router-LSAs and Network-LSAs describe topology; Intra-Area-Prefix-LSAs carry many of the IPv4/IPv6 prefixes associated with that topology.

Why this feature exists

Transit-link prefixes consume LSDB memory and flooding bandwidth even when no application needs to reach them. Prefix suppression hides selected locally configured transit prefixes while preserving the topology graph needed by SPF. Cisco also calls out the security benefit of making internal transit addressing less reachable.

Architecture, control-plane sequence and data-plane consequence

The router still forms OSPFv3 neighbors and advertises the links required for SPF. Suppressed local prefixes are omitted from the relevant prefix LSAs. Loopbacks, secondary addresses, and passive-interface prefixes are not globally suppressed because typical designs need those addresses reachable. Interface-level configuration can override global behavior.

Command / GUI / API teaching

prefix-suppression

At the OSPFv3 process/address-family level, asks the router not to advertise eligible local interface prefixes. It does not disable the underlying OSPF link.

ospfv3 prefix-suppression

At interface scope, controls suppression for that interface and takes precedence over the global setting where documented.

show ospfv3 database

Proves which topology and prefix LSAs are actually present. Neighbor Full alone cannot prove a prefix was intentionally suppressed versus accidentally missing.

Expected versus abnormal state and evidence-first troubleshooting

A NOC sees Full adjacencies but cannot ping a transit subnet and assumes OSPF is broken. The first discriminating check is whether that subnet is intentionally absent from Intra-Area-Prefix-LSAs. If loopbacks disappear too, the problem is not the expected global suppression behavior.

Design, release and multivendor caveat

A device suppresses its own locally configured prefixes; it does not use this feature as a generic filter for prefixes learned from other routers. Use routing policy or area design for other filtering goals.

Reproducible lab

Build three OSPFv3 routers with loopbacks and two transit links. Capture the LSDB, enable global prefix suppression, and identify which LSAs and RIB entries disappear while adjacency and end-to-end loopback reachability remain.

Active recall: Why can OSPFv3 keep a complete SPF topology even when transit subnet prefixes are removed from its prefix LSAs?

3. Cisco Systems — BGP Maximum-Prefix and discard-extra

Platform/release: Cisco IOS XE 17.x
Source/update: Official Cisco guide; current version verified 2026-09-03

Exact source: https://www.cisco.com/c/en/us/td/docs/routers/ios-xe/ip-routing/b-ip-routing/m_irg-max-prefix.html

Beginner foundation — terms you need before this lesson

BGP can receive hundreds of thousands or millions of NLRI entries from a peer. Maximum-prefix is a safety control that limits how many prefixes a neighbor may contribute. Newer IOS XE supports a discard-extra behavior that drops excess prefixes without tearing down the BGP session.

Why this feature exists

A route leak can exhaust memory or destabilize a device long before operators can react. Maximum-prefix is a containment boundary. The operational tradeoff is whether exceeding the threshold should reset the peer, warn only, restart later, or keep the session up while refusing additional prefixes.

Architecture, control-plane sequence and data-plane consequence

Prefixes arrive from a peer → inbound processing counts them → threshold policy decides whether they remain eligible → ordinary BGP policy/best path continues for accepted routes. With discard-extra, excess routes are dropped while the TCP/BGP session remains established. Cisco warns this can create different route visibility on the two peers, so containment must be planned with forwarding consequences in mind.

Command / GUI / API teaching

neighbor <peer> maximum-prefix <limit>

Defines the allowed prefix scale for a neighbor. The configured number is a guardrail, not proof of current usage.

show bgp neighbors <peer>

Use neighbor statistics to compare received/accepted prefix counts and determine whether the threshold was reached.

maximum-prefix ... discard-extra

Keeps the session from flapping while dropping excess prefixes on supporting releases; verify exact platform/release semantics before using it.

Expected versus abnormal state and evidence-first troubleshooting

Traffic fails only for recently announced prefixes while the BGP session remains Established. That is exactly the signature discard-extra can create. Check prefix counters and whether the missing NLRI arrived after the threshold before changing next-hop or LOCAL_PREF.

Design, release and multivendor caveat

Cisco documents per-neighbor logging improvements and discard-extra behavior in newer IOS XE releases. A safety feature that keeps a session up can make the failure less obvious, so telemetry on threshold crossings is essential.

Reproducible lab

Advertise a controlled set of lab prefixes above a low maximum-prefix limit. Compare default session-reset behavior with warning-only and discard-extra. Record BGP session state, accepted-route count and which destinations fail.

Active recall: How can BGP stay Established while new destinations vanish after a route leak, and what counter proves the reason?

4. Palo Alto Networks — PIM Assert Forwarder Election

Platform/release: PAN-OS / NGFW multicast
Source/update: Official PAN-OS multicast documentation; current

Exact source: https://docs.paloaltonetworks.com/ngfw/networking/ip-multicast/pim/pim-assert-mechanism

Beginner foundation — terms you need before this lesson

On a shared Ethernet segment, more than one PIM router might try to forward the same multicast (S,G) stream onto the same LAN. PIM Assert is the election that selects one forwarder for that source/group on that multiaccess network.

Why this feature exists

Without Assert, duplicate multicast packets waste bandwidth and may reach receivers multiple times. The mechanism lets routers detect duplicate forwarding and elect the router with the better path back to the source.

Architecture, control-plane sequence and data-plane consequence

A router receives multicast on an interface it already considers an outgoing interface for the same (S,G), indicating duplicate delivery. It sends an Assert with its route metrics. PAN-OS documents the winner order as lowest administrative distance to the source, then best unicast metric, then highest IP address. Losing routers stop forwarding that (S,G) onto the LAN.

Command / GUI / API teaching

Multicast Runtime Stats → PIM Interface

Shows Assert interval and interface multicast state. It proves timer/configuration state, not which source/group currently won.

Multicast Runtime Stats → multicast forwarding table

Use the (S,G) entry and outgoing-interface list to prove actual multicast forwarding state.

Unicast route lookup to source

Because Assert compares route quality toward the source, inspect the unicast route that supplies those metrics.

Expected versus abnormal state and evidence-first troubleshooting

Two firewalls forward identical multicast streams onto one receiver VLAN. Do not start with IGMP membership if receivers are already getting duplicates. Prove both routers consider the VLAN an outgoing interface, then inspect Assert winner metrics and asymmetric unicast source reachability.

Design, release and multivendor caveat

Assert is not the same as PIM DR election. The DR primarily handles first/last-hop control responsibilities; Assert chooses the multicast packet forwarder for a specific (S,G) on a multiaccess segment.

Reproducible lab

Place two PIM routers on the same receiver LAN with different unicast metrics to a source. Force both initially to forward, observe Assert, then change the unicast metric and predict the new forwarder.

Active recall: Which three tie-break stages does PAN-OS document for PIM Assert, and why is that different from DR election?

5. Palo Alto Networks — PIM Reverse-Path Forwarding and separate mRIB/mFIB

Platform/release: PAN-OS / NGFW multicast
Source/update: Official PAN-OS multicast documentation; current

Exact source: https://docs.paloaltonetworks.com/ngfw/networking/ip-multicast/pim/reverse-path-forwarding

Beginner foundation — terms you need before this lesson

Multicast forwarding verifies packets based on where they came from, not just where they are going. Reverse-Path Forwarding (RPF) asks: 'Would my routing system send unicast traffic back toward this source through the same interface on which this multicast packet arrived?'

Why this feature exists

RPF prevents multicast loops and creates the upstream direction of the multicast tree. PAN-OS also distinguishes the multicast routing information base (mRIB) from the multicast forwarding table (mFIB), which is critical when unicast and multicast paths differ.

Architecture, control-plane sequence and data-plane consequence

Multicast packet arrives → firewall looks up source reachability according to its RPF rules → incoming interface must match the expected upstream path → successful state can create/maintain (S,G) or (*,G) entries → mFIB replicates the packet toward interested receiver interfaces. PAN-OS notes that multicast-SAFI BGP routes can be used for RPF when configured.

Command / GUI / API teaching

View IP Multicast Information

Inspects mRIB/mFIB, incoming interface and outgoing-interface list. This is more useful than looking only at the unicast route table.

Unicast route lookup to source

Determines the default RPF expectation when URIB contributes to lookup.

Multicast route table

Proves multicast-specific source reachability where mRIB is used; a unicast route can be healthy while the selected multicast RPF route differs.

Expected versus abnormal state and evidence-first troubleshooting

Receivers have valid IGMP membership and PIM neighbors are up, but counters show multicast arriving and being dropped. Compare packet ingress with the RPF interface for the source. An asymmetric unicast change can break multicast without touching PIM adjacency.

Design, release and multivendor caveat

RPF success is source-specific. A default route that reaches the RP does not automatically make every source valid. The Advanced Routing Engine also offers explicit RPF lookup modes in current multicast configuration.

Reproducible lab

Create two possible unicast routes back to one multicast source. Move the preferred route without changing PIM neighbors and observe the RPF interface and traffic acceptance change.

Active recall: Why can a unicast routing change break multicast while PIM neighbors and receiver memberships remain healthy?

6. Palo Alto Networks — ECMP Symmetric Return

Platform/release: PAN-OS virtual router ECMP
Source/update: Official PAN-OS help; current 11.1 documentation

Exact source: https://docs.paloaltonetworks.com/ngfw/help/11-1/network/network-virtual-routers/ecmp/ecmp-settings

Beginner foundation — terms you need before this lesson

ECMP lets several equal-cost next hops share traffic. A stateful firewall also tracks sessions. Symmetric Return is a PAN-OS ECMP behavior that causes server-to-client return packets to leave through the same interface on which the associated flow originally arrived.

Why this feature exists

Stateful security, upstream anti-spoofing, NAT, and asymmetric provider paths can make normal ECMP hashing unsuitable for return traffic. Symmetric Return preserves the ingress/egress pairing for the session even if a different ECMP path would otherwise hash as best.

Architecture, control-plane sequence and data-plane consequence

Client-to-server packet enters one ECMP interface → PAN-OS creates session state → server-to-client return packet matches that session → Symmetric Return overrides normal ECMP load-balancing and selects the original ingress interface. The setting therefore operates at the session-forwarding decision, not at BGP/OSPF best path.

Command / GUI / API teaching

Network > Virtual Routers > Router Settings > ECMP

Shows whether ECMP and Symmetric Return are enabled. Changing ECMP can restart the virtual router and can affect existing sessions.

Session browser / session CLI

Proves the actual ingress/egress interfaces selected for a live flow; routing table alone cannot prove session pinning.

Strict Source Path

A separate ECMP option for locally originated IKE/IPsec traffic; do not confuse it with Symmetric Return for server-to-client session traffic.

Expected versus abnormal state and evidence-first troubleshooting

The route table shows two equal next hops, but every return packet for a server flow exits only one interface—the one where the client packet entered. That can be correct behavior, not failed load balancing. Prove session direction and Symmetric Return before changing ECMP weights.

Design, release and multivendor caveat

PAN-OS documents that Symmetric Return overrides ECMP load balancing for the relevant return direction. Enabling/disabling/changing ECMP can restart the virtual router, so treat it as a change-window operation.

Reproducible lab

Build two equal upstream paths to a server behind the firewall. Generate sessions entering each ISP, verify return-interface pinning with Symmetric Return, then disable it in a lab and compare hashing.

Active recall: At what forwarding stage does Symmetric Return override ordinary ECMP, and what evidence proves it is working?

7. Fortinet — PIMv2 Sparse/Dense Multicast and VRF support

Platform/release: FortiGate / FortiOS 8.0.0
Source/update: Official Fortinet Administration Guide 8.0.0

Exact source: https://docs.fortinet.com/document/fortigate/8.0.0/administration-guide/896987/multicast-routing-and-pim-support

Beginner foundation — terms you need before this lesson

PIM builds multicast distribution trees. Sparse mode assumes receivers are sparse and uses an RP/joins; dense mode initially floods and prunes. A BSR distributes RP information, an RP anchors shared-tree state, and a DR represents a LAN for PIM control responsibilities.

Why this feature exists

One multicast source may serve many receivers more efficiently than sending one unicast copy per receiver. FortiGate can participate as a PIMv2 router and current documentation describes sparse/dense behavior, RP/BSR/DR roles and per-VRF multicast support.

Architecture, control-plane sequence and data-plane consequence

Receiver expresses membership → last-hop router sends PIM join → sparse-mode tree builds toward RP/source using RPF → source-side DR registers source where needed → multicast forwarding entries replicate packets only onto receiver branches. FortiGate can use static, RIP, OSPF or BGP unicast reachability for upstream decisions.

Command / GUI / API teaching

config router multicast

Defines global PIM operating parameters. Configuration presence does not prove PIM neighbors or tree state.

Network > Multicast

GUI view for multicast routing configuration and operational roles.

multicast policy

Fortinet requires explicit multicast policy for traffic crossing firewall interfaces; a correct PIM tree does not automatically prove policy permits the stream.

Expected versus abnormal state and evidence-first troubleshooting

PIM neighbors and mroute state look healthy but receivers still see no traffic. Check the multicast firewall policy before changing RP or unicast routing. Conversely, a permissive policy with failed RPF/tree state cannot create multicast reachability.

Design, release and multivendor caveat

Fortinet documents that multicast routing is not supported in transparent mode. Sparse and dense mode assumptions must match participating routers. Current 8.0 documentation also describes multicast awareness across VRFs.

Reproducible lab

Build one source, RP and two receiver VLANs. Verify sparse-mode join/tree state, remove multicast policy while leaving PIM intact, then restore policy and alter the unicast route used for RPF.

Active recall: Why does a FortiGate need both a valid PIM tree and a multicast policy before receivers can get traffic?

8. Fortinet — RIP, RIPv2 and RIPng behavior

Platform/release: FortiGate / FortiOS 8.0.0
Source/update: Official Fortinet Administration Guide 8.0.0

Exact source: https://docs.fortinet.com/document/fortigate/8.0.0/administration-guide/930517

Beginner foundation — terms you need before this lesson

RIP is a distance-vector IGP. Routers advertise reachability plus hop-count metric rather than a complete topology. A metric of 16 means unreachable. RIPv2 adds classless masks and other improvements; RIPng adapts RIP concepts to IPv6.

Why this feature exists

RIP remains present in small, embedded and legacy enterprise networks. It is also an excellent way to reason about route aging, split horizon, passive interfaces, authentication, default-route origination and redistribution because its control model is intentionally simple.

Architecture, control-plane sequence and data-plane consequence

FortiGate sends periodic updates on enabled networks/interfaces → neighbor increments hop count → local RIP process selects the lowest usable metric → candidate competes in the global RIB → FIB is programmed. Passive/send/receive settings can make one direction silent without disabling local route installation.

Command / GUI / API teaching

config router rip

Creates IPv4 RIP process/network/interface policy. Inspect version and network statements before debugging individual routes.

config router ripng

Uses the IPv6 RIPng process where required; do not assume IPv4 RIP configuration automatically applies to IPv6.

get router info routing-table rip

Shows which RIP routes won into the routing table; neighbor updates may exist even when another source wins globally.

Expected versus abnormal state and evidence-first troubleshooting

A neighbor receives routes from FortiGate but FortiGate learns nothing back. Check per-interface send/receive and passive settings plus version/authentication before blaming distance. A route absent from the global table may still exist as a worse candidate behind static/OSPF.

Design, release and multivendor caveat

RIP's 15-hop usable diameter and periodic convergence make it inappropriate for many modern cores. Treat it as a bounded edge/legacy protocol and control redistribution carefully.

Reproducible lab

Run RIPv2 across three routers, make one interface passive only, compare one-way advertisement behavior, then add a higher-preference static route and distinguish RIP's protocol state from global RIB ownership.

Active recall: What does metric 16 mean in RIP, and why can a RIP route be learned but still not own the global RIB?

9. Fortinet — BGP Route-Flap Dampening

Platform/release: FortiGate / FortiOS 7.6.6
Source/update: Official Fortinet CLI reference and BGP administration material

Exact source: https://docs.fortinet.com/document/fortigate/7.6.6/cli-reference/225427711/config-router-bgp

Beginner foundation — terms you need before this lesson

A flapping BGP prefix repeatedly appears and disappears. Route-flap dampening assigns a penalty to instability and can suppress an unstable route until its penalty decays below a reuse threshold. Half-life controls how quickly penalties decay.

Why this feature exists

A single unstable edge prefix can trigger repeated best-path recalculation and updates across many routers. Dampening deliberately trades some reachability for control-plane stability by making chronically unstable prefixes temporarily ineligible.

Architecture, control-plane sequence and data-plane consequence

Prefix withdraw/announce events accumulate penalty → suppress threshold is crossed → route is hidden from normal selection/advertisement while penalty decays → reuse threshold is eventually crossed → route becomes eligible again. FortiOS exposes max-suppress time, reachability/unreachability half-life, suppress/reuse thresholds and optional route-map scope.

Command / GUI / API teaching

set dampening enable

Turns on IPv4 route-flap dampening. Its presence does not prove a particular prefix is currently suppressed.

set dampening-suppress / dampening-reuse

Defines the penalty boundary for suppression and re-use. Mis-tuning can hide legitimate recovery for too long.

execute router clear bgp dampening <prefix>

Clears dampening state after a known temporary event; use only after the underlying instability is understood.

Expected versus abnormal state and evidence-first troubleshooting

The BGP session is Established, the peer is advertising a recovered prefix, but the route remains absent locally. Check dampening state/penalty before changing import policy or next-hop. Dampening is intentionally prefix-specific and can outlive the physical fault.

Design, release and multivendor caveat

Modern operators often use dampening selectively rather than indiscriminately because aggressive suppression can worsen availability. Use route-map scope and measured thresholds for the failure domain you actually want to contain.

11. Arista Networks — BGP Prefix Origin Validation with RPKI

Platform/release: Arista EOS multi-agent
Source/update: Arista TOI updated 2025-03-10

Exact source: https://www.arista.com/en/support/toi/tag/rpki

Beginner foundation — terms you need before this lesson

RPKI lets address holders publish Route Origin Authorizations (ROAs) stating which AS is authorized to originate a prefix. A router compares a BGP route's prefix and origin AS against validated ROA data and marks the route Valid, Invalid or NotFound/Unknown.

Why this feature exists

BGP's normal AS_PATH loop prevention does not prove that the first/origin AS is actually authorized to originate the address block. RPKI adds an external authorization signal that routing policy can use against accidental or malicious route hijacks.

Architecture, control-plane sequence and data-plane consequence

EOS connects to an RPKI validator/cache → receives validated prefix/origin data → BGP route arrives → origin-validation state is calculated → route map can prefer, reject, tag or otherwise act on that state → accepted route continues to normal best-path/RIB/FIB. Command / GUI / API teaching

show bgp rpki

Checks validator/cache connectivity and validation data. Healthy cache state does not prove policy is using validation results.

show bgp <prefix>

Inspect per-route origin-validation state along with normal BGP attributes.

route-map matching RPKI state

Converts validation status into routing intent. The most important design choice is what to do with Invalid and NotFound routes.

Expected versus abnormal state and evidence-first troubleshooting

RPKI cache is healthy and the route is marked Invalid, yet it still wins. That can be correct if no route-map rejects/de-prefers Invalid state. Troubleshoot validation generation separately from policy action.

Design, release and multivendor caveat

NotFound is not the same as Invalid: it means no covering ROA establishes an authorization decision. Production policy must account for incomplete RPKI coverage and cache failure modes.

A router may have enough control-plane state to form IS-IS adjacencies before BGP tables, labels, services or hardware are fully ready. The overload bit drains transit traffic during startup or maintenance without completely removing the node from the topology.

13. FRRouting — BGP Monitoring Protocol (BMP)

Platform/release: FRRouting latest
Source/update: Official FRR latest documentation

Exact source: https://docs.frrouting.org/en/latest/bmp.html

Beginner foundation — terms you need before this lesson

BMP is not another routing protocol that changes forwarding. It is a monitoring protocol defined by RFC 7854 that exports BGP observations—such as pre-policy, post-policy, Loc-RIB and statistics—to a collector.

Why this feature exists

Ordinary BGP show commands answer what one router knows now. BMP gives a centralized observer a continuous feed of what routes were received, rejected, selected and changed, making policy troubleshooting and route-leak forensics much easier.

Architecture, control-plane sequence and data-plane consequence

bgpd receives BGP update → FRR can expose pre-policy Adj-RIB-In, post-policy state or Loc-RIB through BMP → collector records timeline. Route mirroring can export raw BGP messages. FRR implements BMP as a loadable bgpd module, so it must be started with BMP support before configuration can work.

Command / GUI / API teaching

bgpd -M bmp

Starts bgpd with the BMP module. If bgpd was started without it, later CLI configuration cannot magically enable the module.

bmp monitor AFI SAFI pre-policy|post-policy|loc-rib

Selects which BGP processing stage is exported. The stage matters when proving whether policy rejected a route.

bmp mirror buffer-limit

Bounds memory for route-mirroring buffering; if exhausted, FRR reports lost mirroring messages while route monitoring remains a separate mechanism.

Expected versus abnormal state and evidence-first troubleshooting

The collector shows post-policy and Loc-RIB data but not the original rejected route. If pre-policy monitoring was never enabled, the absence does not prove the peer failed to send it. Choose the BMP feed that matches the troubleshooting question.

Design, release and multivendor caveat

FRR documents RFC 7854 version 3 behavior and specific implementation limitations. BMP is observability; it must not be mistaken for a control plane that fixes the route.

14. FRRouting — VRRPv2/v3 on Linux

Source/update: Official FRR latest documentation

Exact source: https://docs.frrouting.org/en/latest/vrrp.html

Beginner foundation — terms you need before this lesson

VRRP provides a shared virtual gateway IP/MAC for hosts. One router is Master and forwards for the virtual address; backups monitor advertisements and take over if the Master fails.

Why this feature exists

Hosts often have only one configured default gateway. VRRP decouples that gateway identity from one physical router so first-hop failure does not require endpoint reconfiguration.

Architecture, control-plane sequence and data-plane consequence

VRRP group elects Master → Master owns/advertises virtual MAC/IP → hosts ARP/ND toward virtual gateway → backups receive advertisements → on failure, timer/election promotes a backup → Linux/macvlan state and FRR cooperate to make the virtual forwarding identity active. VRRP state is separate from the routing table behind the gateway.

Command / GUI / API teaching

show vrrp

Influences election based on local failure signals; validate exact FRR release syntax before production.

ip route / show ip route

Proves the elected gateway can actually forward upstream after it wins.

Expected versus abnormal state and evidence-first troubleshooting

Clients can ARP the virtual gateway after failover but Internet traffic fails. VRRP succeeded; the backup router lacks the required upstream route/NAT/policy. Move immediately from first-hop state to RIB/FIB and external service dependencies.

Design, release and multivendor caveat

FRR documents VRRP support on Linux 5.1+ and does not implement Accept_Mode. VRRPv2 authentication methods are not supported because the RFC considers them deprecated and not meaningful security.

15. FRRouting — NHRP shortcuts and DMVPN-style spoke-to-spoke reachability

NHRP is an ARP-like resolution protocol for NBMA networks. A Next Hop Server (NHS/hub) stores mappings; Next Hop Clients (NHCs/spokes) register and query mappings so peers can build direct shortcuts. Cisco DMVPN uses this general model.

Why this feature exists

A hub-and-spoke overlay is simple but forces spoke-to-spoke traffic through the hub. NHRP lets a spoke learn the NBMA/tunnel address of another spoke and create a direct path while a real routing protocol still carries prefixes.

Architecture, control-plane sequence and data-plane consequence

Spoke registers tunnel/NBMA mapping with NHS → routing protocol learns remote prefix through hub → traffic triggers NHRP resolution for the remote spoke → direct shortcut mapping/route is installed → subsequent packets bypass hub. Command / GUI / API teaching

show ip nhrp

Inspects learned/registered NHRP mappings. A mapping proves address resolution, not that the routing protocol selected a usable spoke prefix.

show ip route

Checks whether the destination prefix points to a route that can exploit the shortcut.

tunnel/GRE and IPsec state

NHRP can know a mapping while the actual NBMA transport or security association is unusable.

Expected versus abnormal state and evidence-first troubleshooting

Spokes register successfully to the hub and can reach each other through it, but no direct shortcut forms. Check route ownership and NHRP resolution/redirect behavior before touching BGP attributes. If the mapping exists but direct packets fail, move down to GRE/IPsec/underlay.

Design, release and multivendor caveat

FRR's NHRP implementation depends on Linux networking and external IPsec tooling in many deployments. Treat NHRP mapping, routing protocol, tunnel device, and security association as four separate state boundaries.

16. Juniper Networks — TCP Authentication Option (TCP-AO) for BGP and LDP

Platform/release: Junos OS 20.3R1+ on supported MX/PTX

BGP and LDP use TCP. TCP MD5 authenticates segments with one shared key and algorithm. TCP-AO (RFC 5925) supports stronger algorithms and keychains with multiple keys so credentials can rotate without necessarily tearing down the TCP session.

Why this feature exists

Long-lived routing sessions need key rotation. A security mechanism that requires a session reset every time a key changes creates an availability tradeoff. TCP-AO provides algorithm agility and coordinated key transitions.

Architecture, control-plane sequence and data-plane consequence

Keychain has timed keys with send/receive IDs → TCP derives traffic keys using HMAC-SHA1-96 or AES-128-CMAC-96 → every TCP segment carries an authentication MAC → BGP/LDP session establishes only when peer authentication expectations align → later key activation can regenerate traffic keys without rebuilding the higher-layer routing session.

show bgp summary / show ldp session

authentication-key-chain ... authentication-algorithm ao

Associates the keychain to BGP/LDP at the documented hierarchy; TCP-AO and TCP MD5 cannot both protect the same connection.

Expected versus abnormal state and evidence-first troubleshooting

BGP TCP reachability is good but the session drops exactly at key rollover. Compare active key, clock, send-id/recv-id reversal and algorithm on both peers before clearing BGP. Key rotation is a transport-authentication boundary, not a BGP best-path problem.

Design, release and multivendor caveat

Juniper recommends spacing key start times and documents constraints on changing active IDs/keychains. Platform/release support and NSR behavior must be verified for the deployed system.

20. Aruba/HPE — IGMP Snooping to constrain Layer-2 multicast flooding

IGMP is the host-to-router membership protocol for IPv4 multicast. IGMP snooping is a Layer-2 switch function: it listens to IGMP control traffic and learns which switch ports actually need each multicast group, so the switch does not flood every multicast frame to every port in the VLAN.

Why this feature exists

Without snooping, Layer-2 multicast behaves much like broadcast and can consume bandwidth or CPU on hosts that never joined the group. Snooping turns receiver membership into a selective Layer-2 forwarding list.

Architecture, control-plane sequence and data-plane consequence

Host sends IGMP report → switch snoops membership → group/port entry is created → multicast frame arrives → bridge replicates only toward interested ports plus required router ports → leave/timeout removes membership. PIM is a Layer-3 tree protocol and is not required simply to constrain forwarding inside one VLAN.

show mac-address-table / interface counters

Helps confirm whether multicast replication reaches unexpected access ports.

Expected versus abnormal state and evidence-first troubleshooting

Every desktop port in a VLAN receives a high-rate video multicast even though only two receivers joined. The routing core can be perfectly healthy; inspect IGMP snooping state and querier/router-port learning on the access switch.

Design, release and multivendor caveat

Snooping relies on valid IGMP control traffic and a working querier environment. Fast-leave behaviors must be used carefully on ports that might contain multiple receivers behind another switch/AP.

Beginner foundation — terms you need before this lesson

Spanning Tree prevents Ethernet loops. MSTP (IEEE 802.1s/802.1Q) lets many VLANs share a small number of spanning-tree instances. An MST region is a set of switches with matching region name, revision and VLAN-to-instance mapping. MSTI 0 is the Internal Spanning Tree (IST); regions connect through the Common Spanning Tree (CST).

Why this feature exists

Per-VLAN spanning trees can consume control-plane resources at scale. One tree for all VLANs wastes redundant links. MSTP groups VLANs into a manageable number of instances while allowing different VLAN groups to prefer different physical paths.

Architecture, control-plane sequence and data-plane consequence

Switches compare MST region configuration → matching devices appear as one region externally → each MSTI computes its own internal tree → IST represents region connectivity → CST connects regions → VLAN frames follow the instance to which their VLAN is mapped. A region mismatch can make two intended members appear as separate regions without any physical link failure.

Command / GUI / API teaching

show spanning-tree mst

Inspects region/instance state, root and port roles. An interface forwarding in MSTI 1 does not imply it forwards for VLANs mapped to MSTI 2.

MST region name/revision/VLAN mapping

All three form the region identity. Matching only the region name is insufficient.

show spanning-tree

Use CST/IST and per-instance views to separate inter-region from intra-region path selection.

Expected versus abnormal state and evidence-first troubleshooting

Two neighboring switches have the same MST region name but one link becomes a region boundary and VLAN pathing differs from the design. Compare revision and VLAN-to-instance digest/mapping before changing STP costs.

Design, release and multivendor caveat

MSTP interoperates with STP/RSTP and only partially with PVST behavior. A multivendor boundary requires explicit root-placement and region-boundary testing rather than assuming per-VLAN trees map one-for-one.

Reproducible lab

Create one MST region with VLANs 10 and 20 in different MSTIs. Intentionally change one switch's revision or VLAN mapping and observe boundary behavior, root roles and which VLAN path changes.

Active recall: Which configuration elements must match for switches to belong to the same MST region, and why can a mismatch alter VLAN forwarding without a link failure?

Translation rule: translate the state being proved, not the command name. A vendor's “route table,” “protocol table,” “forwarding table,” “hardware entry,” “session,” and “multicast tree” are different checkpoints even when the GUI presents them together.

Evidence-first troubleshooting decision tree

  1. Physical/transport: interface, LACP, VLAN, MTU, TCP authentication, BFD or tunnel transport.
  2. Neighbor/session: EIGRP/OSPF/IS-IS/BGP/PIM/NHRP/VRRP state.
  3. Protocol database: LSDB, Adj-RIB-In, PIM tree, NHRP mapping, RPKI validation, FlowSpec NLRI.
  4. Policy/safety controls: prefix limits, import/export policy, RPKI policy, dampening, export limits.
  5. RIB/RPF: selected unicast route, multicast RPF route, route preference and recursion.
  6. FIB/ASIC/kernel: forwarding entry, multicast replication list, FlowSpec ACL/action, virtual MAC, labels/tunnels.
  7. Packet evidence: counters/captures prove ingress, decision, egress and encapsulation.
  8. Remote/return: receiver membership, downstream delivery, stateful return path and policy.

Protocol interaction highlights

Multicast + unicast: PIM RPF depends on route-to-source state. BGP + policy safety: maximum-prefix, RPKI and dampening can intentionally make received reachability unusable without a session failure. IS-IS + policy: overload may be a protective response rather than adjacency failure. NHRP + routing: mapping resolution does not advertise user prefixes. MSTP + VLANs: a region mismatch changes Layer-2 pathing independently of routing.
