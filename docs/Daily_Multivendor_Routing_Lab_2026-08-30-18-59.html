1. Cisco — Understanding routed overlay networks

Official • IOS XE 26.x.x • updated April 10, 2026
Source: https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst_standalones/Multihoming/multihoming-in-bgp-evpn-vxlan-fabric/routed-overlay-mh/understanding-routed-overlay-network.html

Design intent and topology

A routed overlay is a dependency graph, not one feature. Use leaf/distribution pairs connected by a routed spine/core, with downstream CEs or access blocks dual-homed where needed. Cisco’s routed-overlay approach deliberately bounds Layer-2 failure/BUM domains and uses hierarchical BGP plus EVPN multihoming so remote reachability is routed rather than turning every block into one broadcast domain. Treat CE-facing LACP/Ethernet-Segment state, EVPN route distribution, tenant-VRF route selection and the IP underlay as independent fault domains.

Control plane and packet path

Physical/LACP state establishes the local attachment; EVPN represents the Ethernet Segment and originates MAC/IP or IP-prefix reachability; route targets and spine policy determine which routes leave the block; remote leaves import eligible routes into MAC-VRF/IP-VRF state; local route selection installs an active route; its overlay next hop recursively resolves through the underlay. The data plane then performs the tenant lookup, selects a VTEP, programs VXLAN encapsulation, routes the outer packet through the core and decapsulates at the far VTEP. A healthy EVPN route therefore does not prove the VTEP is forwardable.

Verification, failure evidence and remediation

show bgp l2vpn evpn
show l2vpn evpn
show ip route <remote-vtep>
show ip cef <remote-vtep>
show nve peers
show etherchannel summary
show lacp neighbor

Expected state is a continuous chain from EVPN import to a resolved VTEP and programmed adjacency. The signature “EVPN route present + VTEP route absent” isolates the problem below the overlay control plane. Troubleshoot physical/LACP → ESI/multihoming → EVPN origination/import → tenant RIB → VTEP recursion → FIB/NVE → MTU/counters. Fix the first failed transition rather than tuning unrelated BGP attributes. In mixed vendors, names differ but this state chain is invariant.

Lab and active recall

Establish a Type-5 tenant route between two blocks. Remove only the underlay route to the remote VTEP while keeping EVPN established; record which states remain healthy. Restore it, then filter the prefix at the spine boundary and compare the entirely different evidence.

2. Cisco — EVPN VXLAN Integrated Routing and Bridging

Official • Catalyst 9500 IOS XE 26.x.x • updated April 10, 2026
Source: https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9500/software/release/26-x/configuration_guide/vxlan/26x-bgp-evpn-vxlan-9500-cg/configuring_evpn_vxlan_integrated_routing_and_bridging.html

Design intent and topology

IRB is where EVPN-VXLAN becomes a routed tenant architecture. The engineering choice is asymmetric versus symmetric IRB and distributed anycast gateway versus centralized gateway. In DAG, participating VTEPs present the same first-hop gateway identity so host mobility does not require relearning a new default gateway. In symmetric IRB, an L3VNI carries routed tenant traffic and both ingress and egress VTEPs perform routed lookups; asymmetric IRB relies more heavily on L2VNI presence at remote leaves.

Control-plane and data-plane sequence

Endpoint learning produces RT2 MAC/IP state; tenant prefixes can be represented by RT5; route-target policy imports routes into the correct MAC-VRF/IP-VRF. A symmetric packet flows host → anycast gateway → ingress tenant VRF lookup → L3VNI encapsulation → underlay route to egress VTEP → egress tenant lookup → L2VNI/neighbor delivery. Each lookup is independently testable. A correct RT2/RT5 route plus a wrong L3VNI or unresolved VTEP is still a forwarding failure.

Source-supported verification and caveats

show bgp l2vpn evpn
show nve vni
show nve peers
show ip route vrf <vrf>
show ip cef vrf <vrf> <destination>
show mac address-table
show ip arp vrf <vrf>

Cisco documents that DAG SVIs for the same gateway use the same IP/subnet mask. Centralized gateway has design/platform restrictions, including a single CGW VTEP model in the described design, StackWise Virtual for physical redundancy, and platform/release constraints; HSRP/VRRP are not the described CGW redundancy mechanism. Troubleshoot host gateway identity → SVI/VNI mapping → route type/RT import → tenant RIB → L3VNI → VTEP recursion → egress neighbor. A gateway-MAC mismatch can break mobility even while the EVPN session stays healthy.

3. Cisco — Multihoming in a BGP EVPN VXLAN Fabric

Official • IOS XE 26.x.x
Source: https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst_standalones/Multihoming/multihoming-in-bgp-evpn-vxlan-fabric.html

Mechanics

EVPN multihoming overlays Ethernet-Segment/DF signaling on top of local LACP. LACP determines which physical members collect/distribute; EVPN associates the bundle with an ESI, advertises segment discovery, controls DF behavior for BUM and enables remote aliasing/mass-withdraw. All-active and single-active therefore have different expected forwarding behavior even if the CE sees one logical aggregate.

Evidence and troubleshooting

show etherchannel summary
show lacp neighbor
show l2vpn evpn ethernet-segment
show bgp l2vpn evpn route-type 1
show bgp l2vpn evpn route-type 4
show bgp l2vpn evpn route-type 2
show nve peers

Healthy LACP does not prove both PEs advertise the intended ESI; healthy RT1/RT4 does not prove every CE member is synchronized. Duplicate BUM indicates DF/split-horizon trouble; up/up bundle plus remote blackhole points toward EVPN segment state; correct EVPN state plus local packet loss points toward LACP/VLAN/physical state. Troubleshoot physical → LACP → VLAN → ESI → RT1/RT4 → DF → RT2 → VTEP recursion/FIB.

Lab/interoperability

Fail one CE member, restore it, then change only one PE’s ESI. The latter should preserve LACP while breaking EVPN segment consistency. Do not equate EVPN-MH with vPC, MLAG, VSX or MC-LAG; compare ESI/DF/all-active semantics explicitly.

4. Palo Alto Networks — Configure BGP on an Advanced Routing Engine

Official • PAN-OS Advanced Routing Engine
Source: https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing/configure-bgp-on-an-advanced-routing-engine

Mechanics and packet consequence

ARE separates peer establishment, BGP protocol-RIB state, route-table installation and forwarding. Established proves TCP/BGP only. A route accepted into BGP still competes for active routing-table ownership, and its next hop must recursively resolve. The documentation exposes controls such as local preference (documented default 100), MED behavior, ECMP, graceful restart/shutdown and first-AS enforcement. None substitutes for next-hop reachability.

Network > Routing > Logical Routers > BGP
Inspect received/accepted routes
Inspect BGP RIB best path
Inspect logical-router routing table
Verify the route to the BGP next hop

If the prefix exists in BGP but not the routing table, troubleshoot installation/route preference. If installed but blackholing, move to recursion/adjacency. If received but not accepted, inspect inbound policy. Use next-hop-self only at the intentional boundary where the downstream speaker otherwise cannot resolve the original next hop.

Lab

Learn one eBGP route, add a more-preferred competing route to create “BGP present but inactive,” then remove only next-hop reachability to create “active route but unusable.” Compare evidence.

5. Palo Alto Networks — Create Filters for the Advanced Routing Engine

Official • ARE filters
Source: https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing/create-filters-for-the-advanced-routing-engine

Policy stage is part of policy meaning

Access/prefix/AS-path/community lists and route maps can govern inbound acceptance, redistribution or outbound advertisement. Sequential evaluation and peer-over-peer-group precedence make effective attachment scope critical. Trace one prefix through received route → inbound filter → local BGP RIB → active routing table → redistribution map → destination protocol → outbound filter → advertised route.

Network > Routing > Routing Profiles > Filters
Inspect BGP Filtering Profile
Inspect Redistribution Profile / Route Map
Inspect peer-level versus peer-group settings
Inspect received and advertised routes

A route in local BGP but absent from only one peer means earlier acceptance/redistribution already succeeded: inspect outbound filtering. A source route present but absent from BGP points at redistribution/origination. A route sent by the neighbor but absent locally points inbound. Prevent ambiguity with policy names that encode stage and direction and with explicit terminal behavior.

Lab

Block a connected prefix during redistribution, then permit it locally and block it only outbound to one peer. Record the first missing state in each case.

6. Palo Alto Networks — Configure Route Redistribution

Official • PAN-OS 12.2
Source: https://docs.paloaltonetworks.com/ngfw/networking/configure-route-redistribution

Redistribution as re-origination

Redistribution selects a route from the local RIB and creates a new representation in another protocol. With two redistribution points the route can leave OSPF, become BGP, then return and be re-originated into OSPF unless provenance is carried and explicitly rejected. Preference/AD can change which source route is active and therefore which route becomes eligible for redistribution, making failover policy and loop prevention coupled.

Inspect source routing table
Inspect Redistribution Profile / Route Map
Inspect destination protocol RIB
Inspect tags/communities after export
Inspect return boundary rejection

Validate true origin, every redistribution point, source RIB ownership, export match, provenance marker and explicit return rejection. Symptoms of feedback include route churn, alternating protocol ownership, routes persisting after the true source is removed and repeated metric changes. Use tags/communities as origin markers; preference alone is not history.

Lab

Mutually redistribute OSPF/BGP at two firewalls. Tag OSPF→BGP and reject that marker on BGP→OSPF. Observe the returning route being rejected; then briefly remove the reject in a controlled lab to see re-entry.

7. Fortinet — EVPN support for VXLAN Anycast gateway and Type-5 routing

Release-specific routed EVPN

FortiOS 8.0 adds EVPN IRB, VXLAN anycast gateway and RT5 prefix routing. 8. Fortinet — Route maps

Official • FortiOS 7.6.6
Source: https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/535228/route-maps

Ordering and attachment

FortiOS evaluates route-map rules by ascending numeric rule ID, not visual creation/display order. The same construct attaches to BGP inbound/outbound, redistribution, origination and OSPF/RIP contexts. A rule with correct match logic can therefore be operationally wrong because it executes earlier than expected or because it is attached at the wrong transition.

show router route-map
show router bgp
get router info bgp summary
get router info routing-table all

Sort rule IDs numerically, verify the exact attachment, then inspect route state immediately before and after that policy boundary. A locally accepted route missing from one peer indicates outbound policy; a connected route in the RIB but absent from BGP/OSPF redistribution indicates the redistribution attachment. Fortinet documents permit as the rule default when action is unset, but production policy should remain explicit.

Lab

Create IDs 100, 20 and 60 in that creation order, prove evaluation 20→60→100, then move the same match from BGP inbound to redistribution and compare the first missing state.

9. Fortinet — VXLAN with MP-BGP EVPN

Official • FortiOS 7.6.6
Source: https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/52499/vxlan-with-mp-bgp-evpn

Overlay control plane versus transport

RT2 distributes MAC/IP endpoint information and RT3/IMET supports BUM membership; ARP suppression can reduce flooding. Known-unicast forwarding still requires the local bridge lookup to choose a remote VTEP, the outer VXLAN packet to resolve through the underlay FIB and the far VTEP to decapsulate. EVPN therefore does not remove underlay recursion or MTU requirements.

get router info bgp summary
get router info routing-table details <remote-vtep>
show system vxlan
get l2vpn evpn table <vni>
get system arp

RT2 present + VTEP route absent means underlay failure. Known unicast working but BUM failing points to IMET/replication. Small traffic working but large application payload failing points toward effective MTU after outer headers. Troubleshoot peer → RT2/RT3 → VNI → VTEP RIB/FIB → neighbor → BUM → MTU.

Lab

Establish a healthy L2VNI, withdraw only VTEP reachability, then restore and lower transit MTU. Compare the two failure signatures.

VTI, mapping, underlay and BUM

EOS instantiates VXLAN on Vxlan1, selects a source loopback, maps VLANs to VNIs and uses either EVPN/static flood state for remote destinations. A single wrong VLAN↔VNI binding can break one service while Vxlan1 remains healthy. Routed VXLAN adds SVI/VRF state and, on some platforms, hardware TCAM/recirculation requirements.

11. Arista — Configuring EVPN

Official • EOS 4.36.1F
Source: https://www.arista.com/en/um-eos/eos-configuring-evpn

Multi-domain DCI and D-path provenance

An EVPN DCI gateway terminates an RT5 from one domain and re-originates it into another with different domain context. With dual DCI gateways, the route can return through a second boundary unless domain provenance prevents re-entry. EOS uses domain identifiers and D-path; local preference can choose among candidates but is not durable origin history.

router bgp 65536
 bgp bestpath d-path
 address-family evpn
  domain identifier 1:100
  domain identifier 2:200 remote
show bgp evpn route-type ip-prefix
show bgp evpn detail
show ip route vrf <vrf>

Compare RD, RT, next hop and D-path before/after the DCI. Duplicate RT5 paths may be legitimate redundancy or a returning origin; provenance distinguishes them. A single selected RT5 with failed traffic usually shifts focus to VTEP recursion/FIB rather than D-path. Validate vendor support before assuming a different implementation interprets multi-domain provenance identically.

Logical chassis versus independent routing nodes

MLAG presents one logical LACP/STP system downstream but the peers remain independent routing/forwarding devices. VLAN/trunk consistency, peer-link health and config sanity are local MLAG requirements. EVPN multi-VTEP integration can use different next-hop semantics by route type: multihomed RT2 may use shared MLAG VTEP/router-MAC behavior while RT5 can be advertised by each peer with its local VTEP.

13. FRRouting — EVPN

Official FRRouting project documentation • latest
Source: https://docs.frrouting.org/en/latest/evpn.html

bgpd/zebra versus Linux dataplane

FRR makes the control-plane/data-plane seam visible. zebra discovers Linux bridge/VXLAN/VRF objects over netlink and classifies VNIs; bgpd distributes EVPN NLRI; zebra programs accepted information into kernel routes, bridge FDBs and neighbors. A route can be correct in bgpd while Linux lacks the object needed to forward it.

show bgp l2vpn evpn
show evpn vni
show evpn mac vni <vni> detail
show vrf vni
bridge fdb show
ip neigh show
ip route get <remote-vtep>

Compare FRR and Linux at each stage. A MAC in EVPN but not the FDB, an intended L3VNI classified as L2, or a remote VTEP missing from the kernel route table are different failures. Single VXLAN Device designs use external/vnifilter semantics; L3VNI association is explicit. Large host deployments must also account for Linux neighbor-table scale.

14. FRRouting — BGP

Official FRRouting project documentation • latest
Source: https://docs.frrouting.org/en/latest/bgp.html

advertise-all-vni and the underlay

Under address-family l2vpn evpn, advertise-all-vni enables EVPN-VXLAN and identifies the single underlay VRF used for transport. It does not create the route to a remote VTEP. Route targets can be global/per VNI and BUM can use head-end replication or be disabled. Remote EVPN state therefore still depends on the designated underlay and Linux kernel route resolution.

router bgp 65001

  advertise-all-vni
  flooding head-end-replication
show bgp l2vpn evpn
show bgp l2vpn evpn neighbors <peer> routes
ip route get <remote-vtep>

Verify underlay VRF → VTEP route → EVPN peer → RT policy → VNI route → zebra/kernel → BUM. A second VRF cannot simply become another independent EVPN underlay by duplicating the command. Known-unicast success and BUM success must be tested separately.

15. FRRouting — OSPFv2 Redistribution

Official FRRouting project documentation • latest
Source: https://docs.frrouting.org/en/latest/ospfd.html

External LSA mechanics

zebra supplies an active source route; ospfd redistribution policy permits it; the ASBR originates an external. Normal areas use Type-5; NSSA uses Type-7 with ABR translation. E1 includes internal cost toward the ASBR/forwarding address while E2 is dominated by external metric. The 32-bit external route tag is not interpreted by OSPF and is ideal for provenance. A nonzero forwarding address must itself be reachable through OSPF internal state.

router ospf
 redistribute bgp route-map <name>
 redistribute connected metric <value> metric-type 1
show ip ospf database external
show ip ospf route
show route-map
show ip route

LSA present but route absent moves troubleshooting to forwarding-address reachability and RIB ownership; missing external LSA points at source RIB/redistribution. Mutual redistribution without tag rejection can create feedback. Normalize cross-vendor route preference separately from standards-based LSA behavior.

16. Juniper — EVPN Type 2 and Type 5 Route Coexistence with EVPN-VXLAN

Official Junos OS documentation
Source: https://www.juniper.net/documentation/us/en/software/junos/evpn/topics/concept/evpn-t2-t5-coexist-evpn-vxlan.html

Two valid representations, one forwarding choice

The same destination can be represented by RT2 MAC/IP and RT5 IP-prefix reachability. Junos may prefer one representation and mark the other skipped; the coexistence can consume distinct PFE next-hop resources. Thus a design can be functionally correct yet scale poorly in hardware.

show ethernet-switching mac-ip-table extensive
show route forwarding-table extensive
show route <destination-prefix> table <table-name> extensive
show evpn database

Correlate dest_route_skipped, forwarding-table VxLAN Local and routing-table VxlanLocalRT indicators with the intended active route. A skipped RT2 is not necessarily broken when RT5 is deliberately preferred. Both representations still need remote-VTEP recursion. Preference is not OSPF cost

Junos uses local route preference to select among protocol sources; lower is better. Internal OSPF defaults to 10 while external OSPF defaults to 150 in the cited documentation. OSPF cost ranks OSPF paths; route preference ranks OSPF against IS-IS/BGP/static and other sources. Copying Cisco AD 110 into Junos is therefore conceptually wrong.

set protocols ospf external-preference <value>
