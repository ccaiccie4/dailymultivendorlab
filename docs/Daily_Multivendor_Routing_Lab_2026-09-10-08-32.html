Networking Foundations Primer

State chain: originate/learn → policy → advertise/import → RIB selection → recursive resolution → FIB/adjacency/tunnel/label programming → packet forwarding → remote delivery → return path.

Control plane vs data plane

The control plane learns topology, routes, labels, endpoint mappings and policy. The data plane is the FIB, adjacency, tunnel, label stack, ECMP group or ASIC/kernel object that forwards packets.

Route, prefix, next hop

A prefix describes a destination range; a route is a candidate path; a next hop is the immediate or recursively resolved forwarding target.

RIB, FIB, adjacency

The RIB selects among route candidates. The FIB is forwarding-ready state. An adjacency is the final neighbor/tunnel/label relationship needed to transmit.

Recursive next-hop resolution

BGP and overlay next hops often point to another route. Resolution can recurse repeatedly until it reaches a connected adjacency, tunnel, label object—or fails.

Preference / administrative distance

Different routing protocols can offer the same prefix. The platform uses route-source preference/administrative distance before the winning path is programmed.

Underlay / overlay

The underlay transports infrastructure addresses. VXLAN, EVPN and MPLS overlays build service forwarding on top of that transport.

VXLAN / VTEP / VNI

VXLAN carries L2/L3 tenant traffic inside UDP/IP. VTEPs add/remove encapsulation. A VNI identifies a logical service.

EVPN / RD / RT

EVPN is a BGP family for endpoint and service routes. RD makes VPN routes unique; RT controls which VRFs import/export them.

IRB / anycast gateway

IRB joins bridging and routing. Anycast gateway provides one first-hop identity from multiple fabric nodes.

BUM

Broadcast, unknown-unicast and multicast traffic requires replication or multicast handling because one known remote unicast destination is not available.

Redistribution / policy

Redistribution re-originates routes between protocols. Tags, communities, route maps and prefix lists preserve intent and prevent feedback.

LACP / ESI / DF

LACP negotiates link bundles. EVPN ESI identifies a multihomed segment; DF election coordinates selected BUM forwarding.

VRF / VLAN / trunk

A VRF is an isolated L3 routing table; a VLAN is an L2 broadcast domain; a trunk transports multiple VLANs.

1. Cisco Systems — OSPFv3 Graceful Shutdown

Exact authoritative source: https://www.cisco.com/c/en/us/td/docs/switches/lan/c9000/lyr3-fwd/ospf/ospf-configuration-guide/ospfv3-graceful-shutdown.html

Beginner foundation — terms you need before this lesson

OSPFv3 is a link-state IGP. A normal abrupt interface/process failure removes adjacency after liveness detection. Graceful shutdown is an administrative drain: the router tells neighbors it is leaving so alternate paths can be preferred before maintenance.

Problem / why the feature exists

Maintenance should not look like an unexpected failure. Graceful shutdown lets traffic with alternate paths move away before the OSPFv3 process or interface is actually taken out of service.

Architecture, control-plane and packet/state sequence

Operator initiates shutdown → the interface/process sends OSPFv3 shutdown signaling/update → neighbors recalculate away from the draining adjacency when alternatives exist → adjacency is removed while configuration remains retained → data plane follows the alternate FIB path.

Source-supported configuration and verification

Cisco documents process-level `shutdown` under `router ospfv3` and interface-level `ipv6 ospf shutdown` / `ospfv3 shutdown`. Verify with `show ospfv3 ... interface`. The command drains OSPFv3; it does not administratively shut the physical Ethernet interface.

Failure mode, evidence and lab

If the alternate path is missing or has broken recursion/FIB state, graceful shutdown can still expose an outage. Lab: create two OSPFv3 paths, drain one interface, confirm the route changes before disabling the physical link.

2. Cisco Systems — EIGRP Wide Metrics and RIB Scaling

Exact authoritative source: https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-routing/b-ip-routing/m_ire-wid-met.html

Beginner foundation — terms you need before this lesson

Classic EIGRP metrics were designed when link speeds were much lower. Wide metrics use 64-bit calculations and finer latency/throughput scaling so high-speed Ethernet and port-channels do not collapse into indistinguishable costs.

Problem / why the feature exists

At 10/40/100G and beyond, coarse classic metric scaling can make materially different paths appear equal. Wide metrics restore useful differentiation and support much larger aggregate bandwidths.

Architecture, control-plane and packet/state sequence

Interfaces contribute throughput and latency vectors → named-mode EIGRP calculates a 64-bit composite metric → DUAL selects successor/feasible alternatives → the large metric is scaled for insertion into the platform RIB → CEF programs forwarding.

Source-supported configuration and verification

Cisco documents wide metrics only in EIGRP named mode. `metric rib-scale` controls conversion to the RIB scale; changing it clears and reinstalls EIGRP routes with new RIB metric values. K-value mismatches can prevent adjacency.

Failure mode, evidence and lab

A path-selection discrepancy can be caused by vector inputs, K-values, or RIB scaling rather than DUAL itself. Lab: compare classic and named-mode metrics over 10G/100G paths and inspect route metric scaling.

3. Cisco Systems — BGP Cost Community Point of Insertion

Exact authoritative source: https://www.cisco.com/c/en/us/td/docs/routers/ios-xe/ip-routing/b-ip-routing/m_irg-cost-comm-0.html

Beginner foundation — terms you need before this lesson

The BGP cost community is a non-transitive extended community used inside an AS/confederation to influence best-path selection. It has a point of insertion (POI), an ID, and a cost value.

Problem / why the feature exists

Some designs need a tie-breaker inside the local AS without changing transitive attributes seen by eBGP neighbors. Cost community gives an internal-only preference mechanism.

Architecture, control-plane and packet/state sequence

Route-map sets cost community → iBGP/confederation propagates it when extended communities are sent → BGP reaches the configured POI in best-path selection → lower cost-community ID is compared first, then lower cost value wins for equal IDs → winner is installed.

Source-supported configuration and verification

Cisco documents `set extcommunity cost [igp] <id> <cost>` and `bgp bestpath cost-community ignore` for troubleshooting. The attribute is not passed to ordinary eBGP peers.

Failure mode, evidence and lab

Inconsistent support or partial deployment can create different decisions across routers and loops. Lab: set different cost values at two exits, verify internal propagation, then prove the attribute disappears at the eBGP boundary.

4. Palo Alto Networks — BFD Shared-Session Profile Precedence

Exact authoritative source: https://docs.paloaltonetworks.com/ngfw/networking/bfd/bfd-for-dynamic-routing-protocols

Beginner foundation — terms you need before this lesson

BFD can be consumed by BGP, OSPF, RIP and static routes. When multiple clients use the same source/destination pair, PAN-OS can share one BFD session instead of running duplicates.

Problem / why the feature exists

Shared BFD reduces dataplane overhead, but different protocols can request different BFD profiles. The firewall must choose one timer profile for the shared session.

Architecture, control-plane and packet/state sequence

First protocol/static client requests BFD → session identity is built from common endpoints → later clients with same endpoints register to the same session → PAN-OS chooses the profile with the lowest Desired Minimum Tx Interval; ties follow first-created session behavior → one BFD state notifies all registered clients.

Source-supported configuration and verification

PAN-OS documents that the lowest Desired Minimum Tx Interval wins when shared clients specify different BFD profiles. Static routes can create their session earlier than OSPF because static configuration is instantiated immediately after commit.

Failure mode, evidence and lab

An operator may inspect the OSPF profile and expect its timers, while the active shared BFD session is actually governed by a faster static-route profile. Verify the operational BFD session, not just each client's configured profile.

5. Palo Alto Networks — ECMP Weighted Round Robin

Exact authoritative source: https://docs.paloaltonetworks.com/ngfw/networking/ecmp/ecmp-load-balancing-algorithms

Beginner foundation — terms you need before this lesson

ECMP places multiple equal-cost routes into the FIB. PAN-OS chooses an ECMP path at session creation, not per packet. Weighted Round Robin biases new sessions according to interface weights.

Problem / why the feature exists

Two equal-cost circuits may have very different capacities. Sending half the sessions to a 100-Mbps link and half to a 1-Gbps link can overload the smaller circuit.

Architecture, control-plane and packet/state sequence

Equal-cost routes enter FIB → each egress interface has an assigned weight → new session is assigned according to weighted round-robin distribution → packets in that session remain on the selected path according to session behavior.

Source-supported configuration and verification

PAN-OS documents interface weights from 1 to 255, default 100. Higher weight means the path is selected more often for new sessions. Verify actual ECMP membership before blaming the weighting algorithm.

Failure mode, evidence and lab

Weights do not make unequal BGP routes ECMP-eligible. If only one route reaches the FIB, changing weights has no effect. Lab: build 1:3 weights and count new sessions, not packets.

6. Palo Alto Networks — One Local BGP AS per Virtual Router and Inter-VR Routing

Exact authoritative source: https://docs.paloaltonetworks.com/ngfw/networking/bgp/configure-bgp

Beginner foundation — terms you need before this lesson

A PAN-OS virtual router is an independent routing domain with its own RIB/FIB and routing protocol instances. Each virtual router supports one local BGP AS.

Problem / why the feature exists

Designs needing multiple local AS identities on one firewall must isolate them into separate virtual routers and then explicitly connect those routing domains if traffic must pass between them.

Architecture, control-plane and packet/state sequence

VR-A runs BGP AS X → VR-B runs BGP AS Y → each builds independent RIB → inter-VR static routing points a next hop to the other virtual router → forwarding crosses routing domains only where explicitly configured.

Source-supported configuration and verification

PAN-OS documents one Local AS per virtual router and recommends separate virtual routers plus inter-VR routing when multiple local AS numbers are required.

Failure mode, evidence and lab

Creating a second BGP peer with a different desired local AS inside the same VR does not create a second local BGP process identity. The architectural boundary is the VR, not the peer group.

7. Fortinet — FortiSwitch STP Root Guard

Exact authoritative source: https://docs.fortinet.com/document/fortiswitch/6.4.2/devices-managed-by-fortios/749330

Beginner foundation — terms you need before this lesson

STP chooses a root bridge. Root Guard marks a port as a place where a superior root should never appear. If superior BPDUs arrive there, the switch prevents that port from becoming the path to the root.

Problem / why the feature exists

A misconfigured or hostile access/distribution switch can advertise a superior bridge ID and pull spanning-tree traffic through an unintended path.

Architecture, control-plane and packet/state sequence

Port receives BPDU → STP compares root information → superior BPDU appears on root-guarded port → switch blocks/ignores the superior-root claim on that boundary → intended root remains authoritative.

Source-supported configuration and verification

Fortinet documents enabling root guard on FortiSwitch ports that should never become root-facing. STP must be enabled, and root guard must not be applied to the actual root port.

Failure mode, evidence and lab

Root Guard is not BPDU Guard. Legitimate BPDUs can still be present; the trigger is a superior root claim. Lab: lower the downstream bridge priority and observe the guarded port behavior.

9. Fortinet — FortiSwitch Storm Control with Burst Sizing

Exact authoritative source: https://docs.fortinet.com/document/fortiswitch/7.6.5/fortilink-guide/173291/configuring-storm-control

Beginner foundation — terms you need before this lesson

Storm control rate-limits broadcast, unknown-unicast and unknown-multicast floods. FortiSwitch measures packets per second and can apply global or per-switch/port policy.

Problem / why the feature exists

Loops or faulty endpoints can consume LAN capacity before STP or operations reacts. Storm control contains the blast radius.

Architecture, control-plane and packet/state sequence

Ingress flood-type traffic is counted → configured pps threshold and burst allowance are evaluated → excess matching traffic is dropped → forwarding of traffic below the threshold continues.

Source-supported configuration and verification

Fortinet documents 1–10,000,000 pps rates, 0 to drop all matching packets, traffic-type enablement, and burst-size levels on supported releases/platforms.

Failure mode, evidence and lab

Storm control is containment, not loop repair. An excessively low threshold can drop legitimate ARP/multicast bursts. Lab: generate controlled broadcast bursts and compare drop counters at different burst-size settings.

10. Arista Networks — Cross-AFI Forwarding Equivalence Classes

Exact authoritative source: https://www.arista.com/en/support/toi/eos-4-32-1f

Beginner foundation — terms you need before this lesson

A forwarding equivalence class (FEC) is the hardware/software object that groups forwarding vias for a set of routes. Newer EOS can place IPv4 and IPv6 next-hop vias in one ECMP FEC.

Problem / why the feature exists

Mixed next-hop address families appear in modern BGP designs. Older FEC constraints could prevent one ECMP object from representing both IPv4 and IPv6 vias.

Architecture, control-plane and packet/state sequence

Routing resolves several equal next hops → some vias are IPv4 and others IPv6 → cross-AFI FEC feature builds one forwarding object containing both → ASIC hashes traffic across all valid vias.

Source-supported configuration and verification

Arista documents support for a FEC containing both IPv4 and IPv6 next-hop vias in EOS 4.32.x. Verify route recursion and the programmed FEC, not just BGP multipath state.

Failure mode, evidence and lab

If one next hop fails address-family-specific recursion, it cannot contribute to the final FEC even when BGP regards the path as multipath-eligible.

11. Arista Networks — GRE Tunnel Hardware Counters on 7050X4

Exact authoritative source: https://www.arista.com/en/support/toi/tag/7050x4

Beginner foundation — terms you need before this lesson

GRE tunnel interfaces can be hardware-forwarded. Per-tunnel ingress and egress counters reveal decapsulation and encapsulation in the ASIC rather than relying only on interface-level aggregate counters.

Problem / why the feature exists

When GRE traffic fails, engineers need to distinguish 'packet never arrived', 'decap happened but inner forwarding failed', and 'encap happened but underlay delivery failed'.

Architecture, control-plane and packet/state sequence

Outer GRE packet reaches switch → ingress tunnel counter increments during decapsulation → inner packet is forwarded → egress tunnel encapsulation increments egress counter → underlay transmits.

Source-supported configuration and verification

Failure mode, evidence and lab

Zero egress counter with nonzero ingress isolates the problem after decap but before egress encapsulation. Zero ingress points earlier in the path.

13. FRRouting — BGP Roles and Only-to-Customer Leak Prevention

Exact authoritative source: https://docs.frrouting.org/en/latest/bgp.html

Beginner foundation — terms you need before this lesson

RFC 9234 defines BGP Roles—provider, customer, peer, route-server server/client—to encode the commercial relationship of a session. Roles can drive route-leak prevention.

Problem / why the feature exists

Many route leaks happen because policy assumes the wrong relationship. Negotiated roles let both sides detect mismatches and apply Only-to-Customer semantics.

Architecture, control-plane and packet/state sequence

Source-supported configuration and verification

FRR documents `local-role` values provider, rs-server, rs-client, customer and peer, plus RFC 9234 leak prevention mechanics.

Failure mode, evidence and lab

A TCP session reaching port 179 is not enough; an incompatible negotiated role can block usable BGP establishment/policy. Verify OPEN capability/role state.

15. FRRouting — BGP Enforce First AS

Exact authoritative source: https://docs.frrouting.org/en/latest/bgp.html#enforce-first-as

Beginner foundation — terms you need before this lesson

In ordinary eBGP, the first AS in an incoming AS_PATH should normally be the neighbor's AS. Enforce-first-AS checks that expectation.

Problem / why the feature exists

The check detects malformed/misrepresented external updates and catches some route-server/topology misconfigurations.

Architecture, control-plane and packet/state sequence

eBGP UPDATE arrives → FRR compares leftmost AS_PATH value with configured remote AS → mismatch causes update rejection → session can remain Established while affected NLRI is discarded.

Source-supported configuration and verification

FRR documents `bgp enforce-first-as`. Route servers are a classic design where enforcing the neighbor's AS as first path element may be inappropriate because the route server can preserve client AS_PATH.

Failure mode, evidence and lab

If a route-server client learns zero routes while the session is Up, enforcing first AS can be the exact cause. Do not disable it on ordinary transit peers without understanding the trust tradeoff.

16. Juniper Networks — LDP Longest-Match FEC Resolution

Exact authoritative source: https://www.juniper.net/documentation/us/en/software/junos/mpls/topics/topic-map/ldp-overview.html

Beginner foundation — terms you need before this lesson

Traditional LDP FEC lookup often expects an exact IGP/RIB route for the FEC endpoint. Longest-match lets LDP resolve a FEC through an aggregate or summary instead.

Problem / why the feature exists

Hierarchical IGP designs intentionally hide access loopbacks behind summaries. Exact-match-only LDP would defeat that hierarchy by requiring every endpoint route everywhere.

Architecture, control-plane and packet/state sequence

Source-supported configuration and verification

Junos documents `longest-match` for LDP based on RFC 5283. Verify both the summary route and the resulting LDP FEC/LSP state.

Failure mode, evidence and lab

A summary that points into the wrong region can make the FEC control plane resolve while the downstream LSP is incomplete. Validate label continuity, not only RIB coverage.

17. Juniper Networks — ECMP-Aware BFD for LDP FECs

Exact authoritative source: https://www.juniper.net/documentation/us/en/software/junos/mpls/topics/topic-map/ldp-configuration.html

Beginner foundation — terms you need before this lesson

A single FEC can have multiple equal-cost LDP forwarding paths. One BFD session on only one next hop cannot prove every ECMP member is healthy.

Problem / why the feature exists

An ECMP member can fail while the FEC still looks reachable through another member. Per-path BFD plus periodic LSP traceroute gives visibility to every labeled path.

Architecture, control-plane and packet/state sequence

Periodic LDP LSP traceroute discovers ECMP paths → Junos establishes a BFD session for each discovered path → one path fails → its BFD session logs failure → updated traceroute can rebuild the path/session set.

Source-supported configuration and verification

Junos documents `bfd-liveness-detection ecmp` and requires `periodic-traceroute`; omitting periodic traceroute causes commit failure.

Failure mode, evidence and lab

Configuring BFD for a FEC without ECMP discovery may monitor only one active local next hop. Verify the number of discovered paths and BFD sessions.

Beginner foundation — terms you need before this lesson

Problem / why the feature exists

Modern fabrics/edge designs can receive equivalent forwarding choices from both external and internal BGP. Excluding one class wastes capacity or protection.

Architecture, control-plane and packet/state sequence

BGP compares route attributes and IGP resolution → candidates reach eBGP-vs-iBGP preference stage → allow-external-internal relaxes that distinction for selected prefixes → qualified paths form one ECMP nexthop group.

Source-supported configuration and verification

Junos documents EIBGP multipath from 23.4R1 and allows feature-specific policy to select prefixes. All multipath options for contributors must be consistent.

Failure mode, evidence and lab

The knob does not override earlier differences such as LOCAL_PREF or IGP next-hop cost. Prove candidates are otherwise equal before expecting mixed eBGP/iBGP ECMP.

Exact authoritative source: https://developer.arubanetworks.com/aoscx/v10.13/reference/patch_system-interfaces-interface-name

AOS-CX can control whether traffic is bridged between VXLAN tunnels that map to the same L2VNI. Modes include deny, static-evpn and static-all.

Problem / why the feature exists

Architecture, control-plane and packet/state sequence

21. Aruba/HPE — BGP Maximum AS-Path Length Guard

Exact authoritative source: https://www.arubanetworks.com/techdocs/AOS-CX/10.13/PDF/ip_route_8400.pdf

Beginner foundation — terms you need before this lesson

Every BGP UPDATE can carry an AS_PATH describing the autonomous systems the route has traversed. AOS-CX can impose a maximum AS-path length so unusually long paths are discarded before they become normal candidates.

Problem / why the feature exists

Very long AS paths can be a symptom of pathological prepending, policy mistakes, or undesirable routing information. A global AS-path length guard gives the BGP process a structural acceptance limit that is independent of prefix count.

Architecture, control-plane and packet/state sequence

BGP UPDATE arrives → the AS_PATH is parsed into AS segments → its length is compared with the configured max-AS limit → a path longer than the limit is discarded → acceptable paths continue through ordinary import policy and best-path selection → only selected routes can reach the RIB/FIB.

Source-supported configuration and verification

AOS-CX 10.13 documents bgp maxas-limit <LENGTH>; routes whose AS paths are greater than the configured length are discarded. The documented default is 32. Verify the raw AS_PATH on the missing route and the configured max-AS limit before changing prefix filters.

Failure mode, evidence and lab

An eBGP session can remain Established and ordinary routes can work while only a heavily prepended path disappears. In a lab, advertise otherwise identical prefixes with AS_PATH lengths below and above the configured limit and verify selective rejection.
