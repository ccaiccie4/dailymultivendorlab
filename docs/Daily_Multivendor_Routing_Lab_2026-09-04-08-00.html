Networking Foundations Primer

Universal state chain: learn/originate → policy → advertise/import → RIB selection → recursive resolution → FIB/adjacency/tunnel/label/security-association programming → packet forwarding → remote delivery → return-path proof.

Control plane vs data plane

The control plane exchanges topology, reachability, labels, membership and policy. The data plane is the FIB, adjacency, label/tunnel object, ECMP bucket, or secure association that actually forwards.

Route, prefix, next hop

A prefix is a destination range; a route is one candidate path; a next hop is the immediate or recursively resolved forwarding target.

RIB and FIB

The RIB stores candidates and selects a winner. The FIB is the forwarding-ready representation programmed into hardware or a kernel.

Adjacency

An adjacency is the immediate relationship a protocol or forwarding plane depends on: ARP/ND, IGP neighbor, LDP peer, tunnel endpoint, or MACsec peer.

Recursive next-hop resolution

A BGP/VPN/overlay next hop may require another route lookup, and that dependency must terminate in a usable adjacency or tunnel.

Administrative distance / route preference

Different routing sources can offer the same prefix. Cisco commonly calls the local cross-protocol preference administrative distance; Junos calls it route preference.

Underlay and overlay

The underlay reaches infrastructure endpoints. VXLAN/EVPN/MPLS services sit on top and cannot forward if their transport dependency is broken.

VXLAN, VTEP, VNI

VXLAN adds UDP/IP encapsulation; VTEPs add/remove it; a VNI identifies a logical service. L2VNI is a bridge domain and L3VNI a tenant routing context.

EVPN, RD, RT

EVPN is a BGP family for MAC/IP/prefix/service reachability. RD makes VPN routes unique; RT decides import/export membership.

IRB and anycast gateway

IRB combines bridging and routing. An anycast gateway presents the same first-hop identity on multiple fabric nodes.

BUM traffic

Broadcast, unknown-unicast and multicast traffic needs replication or multicast handling because there is no one known remote unicast destination.

Redistribution

Redistribution re-originates routes between protocols. Tags, communities and route policy must preserve ownership and prevent feedback.

LACP / multichassis

LACP bundles links. MLAG/vPC/VSX/MC-LAG coordinate chassis; EVPN multihoming uses standardized Ethernet-Segment signaling.

ESI / DF

An ESI identifies a multihomed Ethernet segment; DF election chooses which EVPN PE forwards certain BUM traffic toward it.

VRF / VLAN / trunk

A VRF is an isolated Layer-3 routing table; a VLAN is a Layer-2 broadcast domain; a trunk carries multiple VLANs.

1. Cisco Systems — OSPFv3 Max-Metric Router-LSA

Platform/release: IOS XE 17.x

Primary feature lesson source:
https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-routing/b-ip-routing/m_ip6-route-ospfv3-max-lsa-xe.html

Beginner foundation — terms you need before this lesson

A Router-LSA describes a router’s topology links. Max-metric makes transit links appear prohibitively expensive while adjacency stays up.

Why this exists

Use it to drain transit traffic during startup or maintenance without removing the router from OSPF. Cisco can restore normal metrics after a timer or after BGP convergence.

Control-plane / packet-state storytelling

Adjacency remains Full → local router originates max-metric Router-LSA → LSAs flood → remote SPF avoids the router for transit → FIBs move traffic elsewhere. Directly connected/stub reachability can remain.

Command / GUI / evidence teaching

`max-metric router-lsa [on-startup seconds | on-startup wait-for-bgp]` changes the advertised cost. Verify OSPFv3 process/LSDB and remote SPF result; an Up neighbor alone does not prove the drain.

Expected vs abnormal state and evidence-first troubleshooting

If traffic still transits the router, inspect the exact process/address family and locally originated LSA. If it never attracts traffic again, verify that the startup/wait condition cleared.

Design / scale / interoperability caveat

Interoperable idea: stub-router advertisement. It is a controlled IGP drain, not interface shutdown.

Reproducible lab

Triangle lab: enable max-metric on the middle router, prove neighbors remain Full while traffic shifts, then restore normal metrics.

2. Cisco Systems — MPLS LDP–IGP Synchronization

Platform/release: IOS XE MPLS with OSPF/IS-IS

Primary feature lesson source:
https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/mp_ldp/configuration/xe-16-11/mp-ldp-xe-16-11-book.pdf

Beginner foundation — terms you need before this lesson

LDP distributes MPLS labels; the IGP chooses the IP path. If IGP convergence outruns LDP, labeled traffic can be sent onto a link that is not label-ready.

Why this exists

Synchronize the two planes so an IGP link stays unattractive until LDP is ready, reducing MPLS blackholes after link recovery.

Control-plane / packet-state storytelling

Link up → IGP adjacency forms so peer reachability exists → LDP session and label exchange establish → synchronization completes → IGP stops advertising max metric → MPLS traffic can safely prefer the link.

Command / GUI / evidence teaching

`mpls ldp sync` enables synchronization; `no mpls ldp igp sync` exempts an interface. Pair `show mpls ldp neighbor` with IGP metric/state and MPLS forwarding evidence.

Expected vs abnormal state and evidence-first troubleshooting

Healthy OSPF/IS-IS plus missing LDP can keep a link at max metric or blackhole traffic if sync is absent. Verify link, IGP, LDP transport, LDP peer, labels, then FIB.

Design / scale / interoperability caveat

This complements—but does not replace—LDP session protection or IGP fast reroute.

Reproducible lab

Two parallel core paths: recover one path before LDP is ready and compare loss with sync disabled versus enabled.

3. Cisco Systems — BGP Dynamic Neighbors

Platform/release: IOS XE BGP

Primary feature lesson source:
https://www.cisco.com/c/en/us/td/docs/routers/ios-xe/ip-routing/b-ip-routing/m_irg-bgp-dynamic-neighbors.html

Beginner foundation — terms you need before this lesson

A listen range is a prefix from which IOS XE may dynamically instantiate a BGP neighbor. The new neighbor inherits a peer-group template.

Why this exists

Reduce repetitive neighbor configuration in fabrics and large edge designs while keeping an explicit admission boundary.

Control-plane / packet-state storytelling

Inbound TCP/179 arrives from an address inside the listen range → IOS XE creates dynamic neighbor → peer-group policy/AS settings apply → BGP capability and AF negotiation complete → routes are exchanged.

Command / GUI / evidence teaching

`bgp listen range <prefix> peer-group <name>` defines admission; `bgp listen limit <n>` caps peers. Cisco documents a default limit of 100 when no maximum is configured. Use BGP summary/peer-group/neighbor views to prove dynamic membership.

Expected vs abnormal state and evidence-first troubleshooting

Unexpected peers usually mean the range is too broad; legitimate peers can fail when the limit is exhausted or AF activation is missing.

Design / scale / interoperability caveat

Dynamic creation is not dynamic trust. Combine narrow ranges, limits, authentication and route policy.

Reproducible lab

Use a /28 listen range with limit four; bring up four peers, attempt a fifth, then source a peer from outside the range.

4. Palo Alto Networks — BGP Route Reflection

Platform/release: PAN-OS Advanced Routing Engine

Primary feature lesson source:
https://docs.paloaltonetworks.com/ngfw/networking/advanced-routing/configure-bgp-on-an-advanced-routing-engine

Beginner foundation — terms you need before this lesson

iBGP normally does not re-advertise iBGP-learned routes to another iBGP peer. A route reflector may reflect routes to designated RR clients; ORIGINATOR_ID and CLUSTER_LIST prevent reflection loops.

Why this exists

Reduce the iBGP full-mesh requirement and scale the control plane.

Control-plane / packet-state storytelling

Client route enters RR BGP RIB → BGP best-path/policy runs → RR reflects according to client/nonclient rules → clients reject looped reflection attributes → selected route still must win the firewall route table/FIB.

Command / GUI / evidence teaching

Mark a peer as Route Reflector client in the BGP AFI profile, then inspect Peer, Local RIB and RIB Out in runtime stats. Established proves the session, not reflection.

Expected vs abnormal state and evidence-first troubleshooting

Clients can be Established but not learn one another if the RR-client role is wrong. Path hiding can occur when the RR reflects only its selected path.

Design / scale / interoperability caveat

Use redundant RRs and explicit cluster design. An RR is a control-plane role and need not be in the data path.

Reproducible lab

One RR plus two clients: remove direct client peering, prove reflection, then remove one RR-client flag and compare RIB Out.

5. Palo Alto Networks — BGP Confederations

Platform/release: PAN-OS BGP

Primary feature lesson source:
https://docs.paloaltonetworks.com/ngfw/networking/bgp/bgp-confederations

Beginner foundation — terms you need before this lesson

A confederation divides one externally visible AS into internal member sub-ASes. Intra-member and inter-member sessions use different BGP semantics while external peers see the confederation AS.

Why this exists

Scale a large BGP domain and create internal policy boundaries without exposing the internal AS structure to the outside.

Control-plane / packet-state storytelling

Member peers establish inside sub-ASes → confed eBGP-style sessions connect sub-ASes → routes carry confederation path information internally → external advertisement hides the internal confed structure behind the public AS.

Command / GUI / evidence teaching

Configure the Confederation Member AS and correct peering type. Use Peer, Local RIB and RIB Out to compare internal and external path presentation.

Expected vs abnormal state and evidence-first troubleshooting

A member peer configured as ordinary eBGP can change AS_PATH/loop behavior. Export policy may also accidentally expose transition details.

Design / scale / interoperability caveat

Confederations and route reflectors solve full-mesh scaling differently and can be combined only with careful operational design.

Reproducible lab

Build two member sub-ASes plus one true external AS; compare the AS path seen internally and externally.

6. Palo Alto Networks — OSPF Virtual Links

Platform/release: PAN-OS logical router OSPF

Primary feature lesson source:
https://docs.paloaltonetworks.com/ngfw/help/12-1/network/network-routing-logical-routers/network-routing-logical-routers-ospf

Beginner foundation — terms you need before this lesson

OSPF requires all nonbackbone areas to connect to Area 0. A virtual link is a logical Area-0 adjacency carried through a normal transit area between ABRs.

Why this exists

Restore backbone continuity during migrations or temporary topology constraints without building an IP tunnel.

Control-plane / packet-state storytelling

Transit-area OSPF must already work → each ABR references the transit area and remote router ID → virtual adjacency forms → backbone LSAs cross the logical link → inter-area routing resumes.

Command / GUI / evidence teaching

Configure the Virtual Link under the OSPF area and optionally apply a dedicated Timer Profile and Authentication Profile. Verify underlying transit-area reachability before the virtual link.

Expected vs abnormal state and evidence-first troubleshooting

Wrong remote router ID, transit-area mismatch, timer or authentication mismatch leaves the virtual link down even while ordinary IP reachability looks healthy.

Design / scale / interoperability caveat

Treat virtual links as controlled exceptions; they add a hidden dependency on the transit area.

Reproducible lab

Place an ABR away from Area 0, form a virtual link through Area 1, then break only the transit-area reachability to the remote router ID.

7. Fortinet — OSPF NSSA Translator and Type-7 Default Behavior

Platform/release: FortiOS 7.6.6

Primary feature lesson source:
https://docs.fortinet.com/document/fortigate/7.6.6/cli-reference/103419153

Beginner foundation — terms you need before this lesson

An NSSA blocks ordinary Type-5 external LSAs from entering but lets an internal ASBR originate external routes as Type-7. An ABR translates eligible Type-7 LSAs to Type-5 for the rest of the domain.

Why this exists

Allow a branch/regional area to originate external reachability without carrying the entire external-LSA domain.

Control-plane / packet-state storytelling

ASBR redistributes route → Type-7 floods inside NSSA → ABR translator role is evaluated → chosen ABR creates Type-5 outside the NSSA → remote routers install if preferred.

Command / GUI / evidence teaching

`set type nssa`, `set nssa-translator-role candidate|never|always`, and `set nssa-default-information-originate enable|always|disable` are documented controls.

Expected vs abnormal state and evidence-first troubleshooting

A Type-7 inside the area but no Type-5 outside points to translation, not local redistribution. Multiple forced translators can produce unexpected behavior.

Design / scale / interoperability caveat

Translator role is a control-plane ownership decision. Keep redistribution ownership and default-origination policy explicit.

Reproducible lab

Use two ABRs and one internal ASBR; originate one Type-7 and change translator roles while observing external Type-5 state.

Platform/release: FortiOS IPv6 VRF

Primary feature lesson source:
https://docs.fortinet.com/document/fortigate/7.0.5/administration-guide/628640/vrf-with-ipv6

Beginner foundation — terms you need before this lesson

A VRF is an isolated routing table. Route leaking selectively copies chosen reachability between VRFs rather than merging them.

Why this exists

Provide controlled shared-service reachability between isolated tenants or routing domains.

Control-plane / packet-state storytelling

BGP learns IPv6 prefix in origin VRF → `vrf-leak6` route-map selects it → target VRF receives leaked candidate through the specified interface → RIB/FIB installs → firewall policy and reverse route still determine session success.

Command / GUI / evidence teaching

`config router bgp / config vrf-leak6`, origin/target VRF IDs, `set route-map`, and `set interface` define the leak.

Expected vs abnormal state and evidence-first troubleshooting

One-way reachability often means the forward leak exists but the return leak or security policy does not. Verify source RIB, leak policy, target RIB/FIB, reverse path, then policy.

Design / scale / interoperability caveat

A leak is an intentional exception to isolation and should be reviewed like a security boundary.

Reproducible lab

Leak one /64 each direction between two VRFs and prove that unrelated prefixes remain isolated.

Design / scale / interoperability caveat

Fallback is a temporary bootstrap exception, not a substitute for proper LACP.

12. Arista Networks — Resilient ECMP Hashing

Platform/release: EOS 4.36.2F IPv4

Primary feature lesson source:
https://www.arista.com/en/um-eos/eos-ipv4

Beginner foundation — terms you need before this lesson

Ordinary ECMP can remap many flows whenever the next-hop set changes. Resilient ECMP uses a fixed hardware bucket structure so surviving flows keep their mapping as much as possible.

Why this exists

Reduce microbursts, reordering and application churn after a single ECMP member failure.

Control-plane / packet-state storytelling

Route has ECMP members → hardware resilient table maps hash buckets to members → a member fails → only buckets assigned to that member are remapped → surviving flows remain stable.

Command / GUI / evidence teaching

`ip hardware fib ecmp resilience` enables documented resilient behavior for selected prefixes. Route output proves the next-hop set; hash-visibility tools prove predicted flow placement.

Expected vs abnormal state and evidence-first troubleshooting

Routing can be perfectly healthy while flow churn is excessive because ordinary ECMP rehashing is the problem. Hardware resource limits also matter.

Design / scale / interoperability caveat

Resilient ECMP is a forwarding-plane feature, not a BGP/OSPF path-selection algorithm.

Reproducible lab

Generate persistent flows across four ECMP members; remove one member under ordinary and resilient ECMP and compare how many flows move.

MACsec protects Ethernet frames hop by hop. MKA authenticates peers and manages keys; replay protection rejects frames with packet numbers outside the allowed receive window.

Protect wired infrastructure links from eavesdropping, tampering and replay at Layer 2.

Design / scale / interoperability caveat

Platform support and frame overhead/MTU matter. MACsec secures one Ethernet hop, not end-to-end application traffic.

Layered troubleshooting workflow

  1. Physical / link security: carrier, errors, LACP, MKA/MACsec where applicable.
  2. Neighbor/session: OSPF/IS-IS/BGP/LDP/PIM adjacency and negotiated capability.
  3. Protocol database: LSDB, BGP RIB, label bindings, BSR/RP mapping, nexthop group.
  4. Policy/scope: RR client, confederation type, NSSA translator, VRF leak route map, dynamic listen range.
  5. Global RIB / recursion: selected route and every dependent next hop.
  6. FIB / hardware: CEF, kernel, PFE, MPLS label entry, resilient ECMP bucket, secure association.
  7. Packet proof: MTU, encapsulation/encryption, counters, capture, remote delivery, return path.

What a command proves matters as much as what it shows. An Established peer proves a session. It does not prove route acceptance, route ownership, FIB installation, packet delivery, or return reachability.

Redistribution-loop and overlay refresher

These intentionally remain spaced-repetition foundations rather than primary lessons. Mark route provenance at redistribution boundaries and block it on the return boundary. In overlays, separate tenant/EVPN control state from underlay recursion, tunnel programming, MTU, remote endpoint state, and return routing.
